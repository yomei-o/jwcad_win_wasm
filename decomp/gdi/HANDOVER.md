# 円弧の画素が合わない件 —— 引き継ぎ（2026-09-28 時点）

この頁だけ読めば続きが始められるように書いてあります。長い経緯は
[`../../docs/notes-pixels.md`](../../docs/notes-pixels.md) に、全体の
状況は [`../../RESUME.md`](../../RESUME.md) にあります。

## 何が問題か

移植（`jw_port.exe` / WASM）の絵は、同梱の図面 15 枚で**原典と 524 画素**
違います。うち **392 画素が `Ａマンション平面例` の部分円弧**で、残りも
ほとんどが部分円弧です。ほかは片付いています。

**原因は分かっています。移植の作りが原理的に合いません。**
移植は部分円弧を、`src/gen/circle.h` に焼いた**真円の環**から両端のあいだを
切り出して描いています。しかし **GDI の部分弧の環は、同じ枠の真円の環の
部分集合ではありません** —— 224 本のうち 213 本が、真円の環に無い画素を
塗ります（`tools/arcsub.py` が GDI 自身に両方を聞いたもの）。図面が使う
半径でも起きます（半径 24 で 64 本中 51 本、1 本あたり平均 5 画素）。

**直すには GDI の曲線ラスタ化そのものを再現する必要があります。**

## 確定していること

| | |
|---|---|
| 弧は**三次 Bézier** | `BeginPath`/`Arc`/`EndPath`/`GetPath` が `PT_BEZIERTO` を返す |
| 平坦化して描けば `Arc` と同じ画素 | 140 画素で 0 差 |
| 分割は**四分円の境目** | 逆コンパイルでも `bPartialQuadrantArc` として確認 |
| 両端は**与えられた点を通る光線**から | 始点＋掃引ではない |
| 制御点 | GDI と **2 点差**まで寄せた |
| 平坦化の**切り方** | 再帰で半分。こちらの測定では「弦から 0.70 画素」 |
| 平坦化の**点の値** | **これが合っていません** ← いまここ |

## 否定したこと（掘り直さないこと）

* **点は `B(k/8)` ではありません。**半径 61・掃引 2.6 で、片 0 の最初の
  切り口の数学的な値は (59.773, −12.383) なのに GDI は **(60, −13)**。
  最寄りの媒介変数も 0.1308 で 1/8 ではない
* **整数で de Casteljau しているのでもありません。**丸め方 4 通り × 許容
  2 通りで、GDI の 14 点と同じ位置に乗るのは最良でも 4 点
* **端が四分円に揃っていても、真円の環の部分集合とは限りません**
* 2r+2 の枠・rp+1 の枠・真円の分岐・丸め方 6 通り・`+0x44` のビット・
  要素の取りこぼし・Direct2D・円弧の端の取り方 —— どれも違いました

**突き合わせに使った実測**（半径 61・掃引 2.6、`tools/gdiarc.exe` の `odd 9`）:

| **(60, −13)** | (59.773, −12.383) | (60, −12) |
| (56, −24) | (56.250, −23.875) | (56, −24) |

## 逆コンパイルで分かったこと（2026-09-28）

`arc.c`・`flatten.c` がその出力です。**要るものは 2 つのモジュールに
分かれています** —— 弧を Bézier にするところは `win32kfull.sys`、
**平坦化と路は `win32kbase.sys`**（前者からは `__imp_` で呼ぶだけ）。

道筋:

    NtGdiArcInternal（win32kfull）
      → bPartialArc(PARTIALARC, EPATHOBJ&, EBOX&, EPOINTFL&, long, EFLOAT&, …)
      → bPartialQuadrantArc(…)          四分円ごと
      → EPATHOBJ::bFlatten（win32kbase）
      → pprFlattenRec                   ← まだ取っていません
      → BEZIER32::bInit / bNext(POINTFIX*)（または BEZIER64）
      → DDA_CLIPLINE                    ← まだ名前で拾えていません

**`BEZIER32::bNext` の 1 行目が答えです:**

```c
*(int *)param_1       = this[0x24] + (this[0x04] + 0x1000 >> 0xd);
*(int *)(param_1 + 4) = this[0x28] + (this[0x14] + 0x1000 >> 0xd);
```

* 点は**前進差分の累算器**（`this+0x04`・`this+0x14`）から出ます。
  **媒介変数 `t` は出てきません** —— だから `B(k/8)` と合わなかった
* 累算器は `POINTFIX` より **13 ビット細かい**固定小数。出すときに
  `+0x1000`（＝ 2^12、半分）足して `>> 13`、つまり**四捨五入**
* 分割の判定は差分の各段の `max(|dx|,|dy|)` を比べる**整数の比較**で、
  弦との距離を計算してはいません。測った「0.70 画素」はその近似
* 大きさで `BEZIER32` と `BEZIER64` を使い分けます
  （`BEZIER32::bInit` が 0 を返したら 64 ビット版へ）

**角度も `atan2` ではありません。**`vArctan`（`arc.c`）は**表を引いて
線形補間**し、八分円ごとに 90/180/270/360 で折り返します。表は
`DAT_14034aa78` と `gaefAxisAngle`・`gaefAxisCoord`。`EFLOAT` は GDI 自前の
ソフトウェア浮動小数です。

## 次の一手（そのまま始められます）

1. **`BEZIER32::bInit`/`bNext` を C に写す。**`flatten.c` にあります。
   `bInit` は `vBoundBox` で枠を取り、そこから差分を作ります。ARM64 の
   逆コンパイル出力には `extraout_w13` のような欠けがあるので、
   **写すときは逆アセンブリで裏を取ること**（Ghidra を開き直せば見えます）
2. **突き合わせる。**`tmp/gdiarc.exe` の `odd 9` が GDI 自身の折れ線を
   返すので、同じ弧で写したものと 1 点ずつ比べます。ここが合えば
   「平坦化の点の値」は片付きます
3. **残りは線の引き方。**`DDA_CLIPLINE` はまだ名前で拾えていません
   （インライン化の可能性）。`decomp_gdi_box.bat` の当たる名前を増やすか、
   `bFlatten` から呼ばれる先を辿ってください。ここで効くのは
   **折れ線の点が `POINTFIX`（小数部つき）である**ことです ——
   `GetPath` が返す `POINT` はその小数部を**捨てた**もので、
   こちらは捨てられた後の整数どうしを結んでいたので画素が合いませんでした
   （GDI 自身の折れ線 14 点を渡しても 140 画素中 45〜56 が違う、の説明）
4. `pprFlattenRec`（`EPATHOBJ::bFlatten` が呼ぶ本体）も取ること

## この結果の出どころ

`C:\Windows\System32\win32kfull.sys`・`win32kbase.sys`（ARM64、
Windows 11）と、**Microsoft が公開しているそのシンボル**。詳しくは
[`README.md`](README.md)。**Microsoft の著作物から機械的に起こしたもの**で、
読むために置いてあります。移植の答えは今までどおり「原典に描かせた画素」で
確かめること。
