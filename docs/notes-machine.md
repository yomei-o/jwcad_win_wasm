# 機械まわりと、原典の駆動

RESUME.md から分けた作業ノートです。節はそのまま、順番も
そのままにしてあります。本文中の「下記」「上記」は元の並びの
ままなので、別のノートを指していることがあります。

* 別の機械で続けるとき
* ビルドだけ別の機械に逃がすとき（ARM64 Windows）
* ステータス行は読めます（写真は要りません）
* 原典を駆動するときの落とし穴（PowerShell）

## 別の機械で続けるとき

一度やりました（ARM の上のエミュレーションから Intel の Windows 11 へ）。
**基準画像は撮り直さなくてよい**ことが分かっています —— `docs/ref_start.png`・
`docs/ref_test1.png`・`docs/ref_zoku.png` を撮り直して、いずれも文字と
テーマの枠を除いて **0 画素差**でした。GDI のラスタライズも Windows の
フォントも機械をまたいで同じ画素を出します。

条件は一つだけです。

* **画面の拡大縮小を 100% にすること。** `Jw_win.exe` はマニフェストに
  `<dpiAware>true</dpiAware>` を持つ system DPI aware なアプリなので、
  150% のままだと 144dpi で自分を描き直し、字も枠も基準と別物になります。
  `tools/shot.ps1` は窓を 1280×800 にするので作業領域も 800 行以上要ります。

作り直しが要るのは、リポジトリに入らないものだけです。
`sh tools/gen.sh` が全部やります（後半は原典を動かすので 20 分ほど）。
Ghidra は `tools/decomp_box.ps1`（`GHIDRA_HOME` / `JAVA_HOME` /
`GHIDRA_HEADLESS_MAXMEM` を環境から見ます）。8 スレッド 24 GB の機械で
6 シャード・約 13 分、**25,983 関数 / 99.8% / 26 MB** —— ビルドマシンで
出た数と同じでした。

## ビルドだけ別の機械に逃がすとき（ARM64 Windows）

手元の CPU がふさがっているときのために、ARM64 Windows の VM
（`yomei@192.168.11.24`、`C:/prog/jwcad_win_wasm`）で
`sh tools/check.sh` を回せるようにしてあります。送るのは scratchpad の
`sync.sh`（`src tests tools docs font decomp/res` を tar で。`orig/` は
向こうでインストーラから作ること —— 日本語のファイル名が tar で壊れます）。

**そこで分かった落とし穴が三つ。**

* **`PATH=...` を ssh のコマンドの前に付けないこと。**向こうのランチャが
  パスらしいものを書き換えるので `$PATH;C:/prog/...` になり、
  **w64devkit の busybox が唯一の `sh`** になって `/c/...` が開けなく
  なります。`tools/build_tests.sh` は自分で w64devkit を探します。
* **emsdk は arm64 では `emsdk install` が通りません。**中身は入るので、
  `upstream/emscripten/.emscripten` を手で書けば動きます
  （node は 24 系だと `node/<版>/node.exe`。`bin/` がありません ——
  `tools/check.sh` の node 探しも両方見るようにしました）。
* **超越関数の最下位ビットが手元と違います。**同じ実行ファイルで
  `sin`・`cos`・`tan`・`atan2`・`log`・`exp`・`pow` の結果が食い違います
  （`sqrt` は IEEE が一意に決めるので同じ）。x86 のエミュレーションが
  この手のものを向こう側の実装に流しているからだと思われます。
  **そのため `tests/dxf_test.exe` の `orig/Test5.jww -> test5.dxf` だけは
  VM で落ちます** —— 文字の回転角が `atan2` 経由で
  `-100.00000067721582`、手元と原典は `...585`。**VM で何か落ちたら、
  その試験だけ手元で走らせて確かめること。**バイト単位の照合を
  最終的に信じてよいのは手元だけです。

**この 1 ビットは向こうでは直せません。**原典は 32 ビットの MSVC なので
`atan2` は x87 の `fpatan`、つまり**仮数 64 ビットで計算して最後に
double へ丸めたもの**です。移植でも `long double`（x86 では 80 ビット）
を通せば揃うはず——と思って `atan2l` と `fpatan` を直に呼んで測りました
（`tmp/atanprobe.c`、`tmp/build_probe.sh atanprobe`）。

| | `atan2` | `atan2l` | `fpatan` 直接 |
|---|---|---|---|
| 手元（x86_64 native） | `-100.00000067721585` | 同じ | 同じ |
| VM（ARM64 で x64 を走らせる） | `-100.00000067721582` | 同じ | 同じ |

**向こうでは三つとも一致します。**`LDBL_MANT_DIG` は 64 と名乗りますが、
x64 エミュレーションの x87 は**倍精度で回っている**ということです。
`long double` に逃げても意味がないので、`atan2l` を使う変更は入れずに
戻しました。VM は**画素の採点には使えます**（15 枚の合計は手元と
1 画素違わず 973）が、**浮動小数の最下位桁を見る試験の裁定には
使えません**。

## ステータス行は読めます（写真は要りません）

**`read:59393` で原典が今なにを聞いているかが読めます。**ステータス行は
フレームのただの子ウィンドウで、`WM_GETTEXT` がそのまま文字を返します
（`GetWindowText` は他プロセスでは空です —— `tools/jwdraw.ps1` の `TxtMsg`
がその回避です）。

```
read 59393: [ 円を指示してください。     ]
read 59393: [ 円上点を指示してください。   (L)free (R)Read]
read 59393: [ 始点を指示してください  (L)free  (R)Read]
read 59393: [ ◆　　終点を指示してください  (L)free  (R)Read]
```

これで**コマンドの段取りが実測できます** —— 接線の 角度指定・円上点指定 は
この 4 行そのままで分かりました。以前はここを画面写真で確かめていました。

## 原典を駆動するときの落とし穴（PowerShell）

`tools/jwdraw.ps1` を書き直したときに全部踏みました。どれも「エラーが
出ないまま静かに間違う」ので、疑う順に並べておきます。

* **`saveas:` は既存のファイルを上書きしません。**「上書きしますか」の
  確認が出て、そこで止まります。ファイルは前のまま残るので、存在を見る
  だけの確認は通ってしまい、**何度やり直しても前回の結果が返る**という
  形で出ます。いまは保存の前に消しています。
* **`c`（実カーソルを動かしてからクリック）だと拾いません。**
  素の `WM_LBUTTONDOWN` は通ります。ステータス行を見ると、`c` の拾いでは
  「基準線を指示してください。」のまま動かず、次の素のクリックで進みます。
  RESUME の表は `c` で書いてありましたが、**要らないどころか邪魔**です。
  段がどこまで進んだかはステータス行を撮るのがいちばん早い
  （`shot:` してその下 19 行を見る）。
* **`.ps1` は UTF-8 の BOM を付けること。** PowerShell 5.1 は BOM の無い
  `.ps1` を CP932 として読むので、日本語のコメントが化けて**次の行を
  飲み込みます**。`# 名前を付けて保存` の次の行が実行されませんでした。
* **`LP` という名前の関数は作れません。** PowerShell に `lp`
  （`Out-Printer`）のエイリアスがあり、エイリアスが関数より優先されます。
  クリックが全部プリンタに行きました。
* **`GetWindowText` は他プロセスのコントロールの文字を返しません。**
  Edit も ComboBox も空で返ります。`WM_GETTEXT` を送れば読めます
  （`read:<id>` 段）。`bars.txt` のコンボが空なのはこれが理由で、
  Static と Button の文字はウィンドウのタイトルなので普通に読めます。
* **`[void](...)` は中の `Write-Output` ごと捨てます。** 行は `-Out` の
  ファイルには入るのに標準出力には出ない、という形で出ます。
* **関数から `[IntPtr]` を返すのは危うい。** 本体が何か出力していると
  配列になって返り、`-eq [IntPtr]::Zero` が偽になって次で落ちます。
  ハンドルは `$script:` の変数で受けるほうが安全です。
* **拾いは 4 回に 3 回くらいしか通りません。** 同じレジストリ・同じ
  クリックでも、コマンドが 1 段目のまま何も描かないことがあります。
  `tools/refanswers.sh` は図面ごとに対応する検査を回して、食い違えば
  引き直します。

## 刺された罠

**`w64devkit/bin` を PATH の先頭に置いてはいけません。**そこの
`sh.exe`（busybox）が Git Bash の `sh` を隠し、`[ -f /c/prog/... ]` が
**偽**になります —— busybox は MSYS の `/c/...` を知りません。これで
`tools/check.sh` が `emcc not found at /c/prog/emsdk/...`（実際には在る）
で落ちました。各スクリプトは自分で w64devkit を探すので、**PATH も `CC` も
いじらずに `sh tools/check.sh` と打つのが正解**です。


**原典に試させるなら、まず図面を用意すること。**寸法の 3 段目
（寸法の始点）が空の図面ではどう押しても通らず、コマンドの仕様の問題だと
思って長く探しました。**読み取れる点がないと受け取らない**段だったので、
線を 1 本引いてからならすぐ通りました。中心線も同じで、線 2 本を先に
描いてから試すべきでした。原典を動かして確かめるときは、**まず何か描く**。

**バーの数値欄に値を入れるには本物の `WM_CHAR` が要る。**`WM_SETTEXT` で
コントロールの文字を書き換えても、コマンドは自分の持っている値で描きます
（多角形で、寸法を空にしても五角形が同じ大きさで出続けました）。
`tmp/jwdraw.ps1` の `ch:<id>,<文字>` が 1 文字ずつ送ります。

**PowerShell の変数名は大文字小文字を区別しない。** `param([long]$Lo)` の下で
`$lo = $Lo + $i * $step` と書くと**同じ変数**です。分割して逆コンパイルする
`tools/decomp_box.ps1` で、2 番目以降のシャードが「開始 > 終了」になって
黙って 0 関数を出しました。ログは正常、`DONE` も出るので気づきにくいです。
いまは `$rlo` / `$rhi` にしてあります。

**`PrintWindow` では図面が撮れない。** 枠とメニューは返ってきますが、
Direct2D のスワップチェーンは見えないので**作図領域が真っ白**になります。
`tools/shot.ps1 -Screen` はデスクトップから画素を読みます。

**撮影は画面を占有するので最小限に。** `-Screen` は前面に持ってきて
デスクトップから画素を読むので、その間は機械が使えません。15 枚撮るのに
20 分ほどかかります。まとめて一度だけ撮ること。

**原典の描画には当たり外れがある。** 同じ図面・同じレジストリでも、全部
描けるときと途中で止まるときがあります。Ａマンション25d.jww は 11,716 と
2,483 を行き来しました。`tools/shot.ps1 -Tries 3` で三回撮ってインクの
一番多いものを残します（インクは減ることはあっても増えないので）。
「原典が一部の要素を描かない図面がある」という結論に二度たどり着いて
二度とも間違いでした。疑う前にまず撮り直すこと。

**画面の大きさが変わると原典のツールバー配置が崩れる。** MFC は
`ToolBar-Summary\ScreenCX/CY` に配置を保存したときの画面寸法を入れておき、
今の画面と違うと保存した配置を捨てます。レジストリを入れ直しても直らないので
たちが悪い。`sh tools/refenv.sh` が今の画面寸法を書き込んで直します。

**原典は描画を途中で止める。** 図面を開いたときの描画が段階的で、
途中で止まったまま戻ってきません。しかも待っても再開しないので、
「画面が変わらなくなるまで待つ」では途中経過を撮ってしまいます。
`-Repaint`（非表示・再表示）と `-Cmd 32835`（全体再表示）を送ってから、
**プロセスの CPU 時間が伸びなくなるまで**待つこと。画面を見て待つと、
描画の合間の休みで抜けてしまいます（文字を描く前で止まる）。

**`-Repaint` を最小化・復元でやってはいけない。** MFC がツールバーの
配置を `HKCU` に書き戻すので、以降の基準画像の枠が全部変わります。
一度やって 15 枚撮り直しました。非表示（`SW_HIDE`）・再表示
（`SW_SHOWNOACTIVATE`）なら枠はそのままです。壊したときは
`reg delete "HKCU\Software\Jw_cad\jw_win" /f` してから
`reg import tools/refenv.reg` で戻せます。

**`analyzeHeadless` は先にプロジェクトの親ディレクトリが無いと落ちる。**
`Directory not found: C:\prog\jwwin\proj` で止まります。しかも
`launch.bat` がそこで「続行するには何かキーを押してください」を出すので、
ssh 越しだと固まったように見えます。

**Ghidra の `DIALOGEX` 判定。** `DLGTEMPLATEEX` は先頭が
`WORD dlgVer=1; WORD signature=0xffff` です。`signature` だけ見て
`dlgVer` を 1 つ後ろから読むと、ダイアログ 108 枚のうち
`DIALOGEX` のものが全部ずれて `struct.error` になります（一度やりました）。

**Ghidra は `-readOnly` でもプロジェクトを排他ロックする。** 同じ
プロジェクトに 10 個の headless を向けると、最初の 1 つだけが動いて残りは
`Unable to lock project!` で死にます。**それでも実行は `DONE` を出す**ので、
出力が 1 つしか無いことに気づくまで成功に見えます。`tools/decomp_box.ps1` は
プロジェクト（146 MB）をシャードごとに複製します。

**`CData` の共通部で、線色と線種は思う順番の逆。** `+0x28` の 1 バイトが
**線種**（点の形、文字の種類にも使い回される。だから `% 100` される）、
`+0x2a` の 2 バイトが**線色**です。逆に取ると Test1 がほぼ全部水色になります
（`CDataSolid` が `+0x2a == 10` すなわち「任意色」を見るのが決め手）。

**円弧の 7 つの倍精度は「中心 x, 中心 y, 半径, 開始角, 開き角, 傾き, 扁平率」。**
5 番目は終了角ではなく**開き角**です。終了角だと Test1 の隅の丸めが
真円になります。

**背景で撮ると作図領域が当てにならない。** `tools/shot.ps1` の既定
（`PrintWindow`）は**枠は完璧**ですが、作図領域は文字が落ちるだけでなく、
図面によっては**ほとんど描かれていない絵**が返ってきます。
日影図.jww は背景で 7,979 画素、前面で 46,283 画素でした。
撮る前に `RedrawWindow`（`RDW_UPDATENOW | RDW_ALLCHILDREN`）を投げても
変わりません。Jw_cad が作図領域を何から転送しているにせよ、`WM_PRINT` は
そこに届かないということです。
**図面を基準にするときは `-Screen`**。画面を最前面に持ち上げるので、
人が使っている最中には向きません。

**この環境ではシェル越しにバックスラッシュのエスケープが 1 段はがれる。**
Python のヒアドキュメントで C の 16 進エスケープを書こうとすると生バイトが
ファイルに入り、UTF-8 として保存されて化けます。\\
`chr(92)` でバックスラッシュを作るのが確実です
（`src/ui.c` のステータス行の文字列）。

**同じ罠は C の文字列にも効きます。**ヒアドキュメントの中に
`printf("... %s\n", x)` と書くと、`\n` が**本物の改行**になって文字列
リテラルが行をまたいで壊れます（2026-09-26 に 3 回踏みました）。
**エスケープの入るものは、シェル越しではなくファイルに書く道具で書くこと。**
壊れたあとは「引用符の数が奇数の行」を探すのが早いです:

```sh
awk '{n=gsub(/"/,"\"")} n%2==1 {print NR": "$0}' そのファイル
```

**Git Bash から Windows のパスを渡すとバックスラッシュが消える。**
`-Exe orig\Jw_win.exe` が `origJw_win.exe` になります。スラッシュを使うこと。
日本語のファイル名は ssh / PowerShell の間で CP932 に落ちて壊れるので、
`orig/Test1.jww` のような ASCII 名で試すこと。

## 原典を実際に動かして確かめる（画面は撮りません）

`tmp/jwdraw.ps1` は原典を起動して図面を開き、いちばん面積の大きい
子ウィンドウ（ビュー）に `WM_LBUTTONDOWN` / `WM_LBUTTONUP` を投げて、
最後に `WM_COMMAND 57603`（上書）を送ります。キャプチャは一切しません。

**ウィンドウは出さざるを得ません。**`SW_SHOWNOACTIVATE` で出したうえで
`HWND_BOTTOM` に落とし、フォーカスは奪いません。それ以上は無理でした:

* **隠す（`SW_HIDE`）と** Jw_cad が別の大きさで自分を配置し、紙の座標が
  ぜんぶずれます。
* **画面の外や隅に動かすと** MFC がドッキングバーを組み直し、**その配置を
  レジストリに書き戻します**。次の起動で左ツールバーが 2 列から 1 列に
  なり、座標が 39 画素ずれました。`tools/refenv.sh` で戻せます。

つまり「最背面に置く」までが、原典の挙動を変えずにできる限界です。

    powershell -File tmp/jwdraw.ps1 -Cmd 32883 -Clicks '250,180;450,180;450,320'
    powershell -File tmp/jwdraw.ps1 -After 57643          # 最後に元に戻る
    -Open ''              ファイルを開かずに起動する（素の設定で出る）
    -Clicks 'cmd:32794'   途中でコマンドを切り替える
    -Clicks 'r300,200'    右クリック
    -Clicks 'c300,200'    実カーソルもそこへ動かしてからクリック
    -Clicks 'raw:v,5136,0,0'      ビューに任意のメッセージ（これは選択確定）
    -Clicks 'shot:tmp/a.png'      ウィンドウをオフスクリーンに描かせて撮る
    -Clicks 'saveas:x'            名前を付けて保存（下記）
    -Clicks 'bar' / 'box' / 'top' / 'btn:1120' / 'off:1323' / 'type:あ'
    -Clicks 'pb:1147'             BM_CLICK を投げるだけ（下記）
    -Clicks 'm400,350'            クリックせずにカーソルだけ動かす
    -Clicks 'w1197,467[,r]'       フレームのクライアント座標で押す（レイヤの格子）
    -Clicks 'dlg:32807,tmp/a.png' コマンドでダイアログを出して中身を書き出す
    -Clicks 'dlg:b1843,tmp/a.png' 同じことをバーのボタンを押して（直りました）
    -Clicks 'set:1411,12'         バーのコントロールに文字を入れる（ハッチと
                                  寸法のバーには効きます）

**`saveas:` は共通ダイアログを使います。**原典は既定では自前の
「ファイル選択」ダイアログ（リソース 290）を出し、その名前欄 id 1487 は
読み取り専用で `WM_SETTEXT` が効きません。レジストリの
`Dialog\FileCommonDialog` を 1 にすると Windows の共通ダイアログになり、
IDOK で保存できます（**使い終わったら `tools/refenv.sh`**）。名前は
既定のまま（無題.jww、または開いているファイル名）になるので、保存先は
「直前に使ったフォルダ」に出ます。上書き確認が出たら IDYES を送ります。

**`shot:` は `PrintWindow(PW_RENDERFULLCONTENT)`。**画面は読みません。
Direct2D が切ってある（`View_Direct2d = 0`）ので中身もちゃんと出ます。
これで「選択された要素は ff00ff、範囲の枠は ff0000」のような、
保存では分からないことが確かめられます。

**クリックが効かないコマンドがあります。**ビューのボタン処理のなかには
`GetCursorPos` で実カーソルを読むものがあり、そこは `c` 付きでないと
通りません。寸法の 3 段目はそれでも通りませんでした（「寸法」の項）。

**これで分かったこと。**

* **矩形は 4 本の `CDataSen`。** 最初にクリックした角から x 方向 → y 方向
  → 戻る、と一周し、各線は前の線の終点から始まります。クリックの順を
  逆にしても同じ形なので、**絶対座標ではなく最初のクリック基準**です。
  ファイル形式に矩形はありません。
* **連続線は 1 本分ためる。** n 回クリックして保存すると **n−2 本**。
  2 回で 0 本、4 回で 2 本、5 回で 3 本。最後の 1 本は画面に出ているだけで、
  次のクリックが来て初めて図面に入ります。
* **元に戻るはコマンド単位。** 矩形を描いて `-After 57643` すると 46 本に
  戻りました（4 本まとめて）。要素 1 つずつではありません。
* **消去は右クリックで図形消去、左クリック 3 回で部分消し。**
  矩形の一辺の上で右クリックすると 50 本が 49 本になり、消えるのは
  その辺でした。左クリックは 1 回目が図形の選択、2・3 回目が消す範囲で、
  3 回目で初めて実行されます（だから 1 回や 2 回では何も起きません）。
* **原典と同じ座標を出すところまで確かめました。** 画面 y=300 に線を引き、
  (400,300) で選んで (350,330)・(450,270) で切ると、原典は
  `-263.230,37.233 → -176.641,37.233` と `-90.052,37.233 → 39.831,37.233`
  の 2 本を残します。移植も**同じ数字**になりました（`tests/click_test.c`）。
  つまり範囲の 2 点は線に**垂線の足として投影**されます。
* **ビューの原点差は (78, 34)。** 原典の描画子ウィンドウのクライアント座標に
  78 と 34 を足すと、この移植のフレームバッファ座標になります。倍率は
  同じ（Test5 で 1.154882 画素/mm）なので、`cmd:32835`（全体表示）を
  送ってから座標を計算すれば移植側で当たりを予測できます。
  実カーソルを重ねる必要もないので、`c` 付きのクリックはもう要りません
  （ビューは `GetCursorPos` も読んで `view+0x23d0` に置きますが
  〈`FUN_00517290`〉、拾い上げに使うのは lParam の方〈`+0x23d4`〜〉です）。

## ブラウザで文字を打たせるまでに踏んだ穴

動くまでに四つ躓いたので書いておきます。どれも「打っても何も起きない」と
いう同じ見え方をするので、切り分けの順番が大事でした。

1. **`jw_key` などを `EXPORTED_FUNCTIONS` に入れ忘れていた。** C を足した
   だけでは wasm から出てこない。ネイティブは同じ C を直接呼ぶので気付け
   ない。`node -e "require('./jwcad.js')().then(m => ...)"` で
   `typeof m._jw_key` を見るのが早い。
2. **新規図面に文字書式が無かった。** 幅 0 では置かない実装なので黙って
   落ちる。`app_new` に原典の既定（W=3.5 H=3.5 D=0 色 2）を入れた。
3. **`app_key` が絵を作り直していなかった。** ネイティブは呼び出し側で
   `app_paint` していたので動き、ブラウザだけマウスを動かすまで出なかった。
   いまは `app_key` / `app_compose` の中で作り直す。
4. **`jwcad.js` がキャッシュされていた。** wasm は `locateFile` で毎回
   新しく取りに行くようにしていたので、**新しい wasm ＋ 古い糊**という
   いちばん分かりにくい状態になった。`?v=` を上げるのと、糊に必要な関数が
   無ければ赤い帯で言うようにした。

**IME の未確定文字列は自分で描く必要があります。**原典の入力窓は本物の
Edit なので未確定も勝手に出ますが、こちらは自前描画なので
`compositionupdate`（ネイティブは `GCS_COMPSTR`）を拾って下線付きで描いて
います。これが無いと「IME をオンにすると Enter まで何も出ない」ように
見えます。

`?debug=1` を付けて開くと、右下に build 番号と、文字コマンドの状態
（focus の有無・変換中の文字列・確定した文字列）が出ます。

## Ghidra をビルドマシンで回す

192.168.6.14 に Ghidra 12.1.3 と Temurin JDK 21 が入れてあります
（`jwcad_dos_wasm` の `tools/build_box_setup.ps1` で入れたもの。同じ版なので
ラップトップと出力が一致します）。5.5 MB の `.text` はラップトップで
解析すると一日仕事なので、ここは必ずビルドマシンを使います。

```sh
scp -i ~/.claude/keys/ort_build_key orig/Jw_win.exe yomei@192.168.6.14:C:/prog/jwwin/bin/
ssh -i ~/.claude/keys/ort_build_key yomei@192.168.6.14 'C:\prog\jwwin\analyze_box.bat'
ssh -i ~/.claude/keys/ort_build_key yomei@192.168.6.14 'C:\prog\jwwin\inventory_box.bat'
ssh -i ~/.claude/keys/ort_build_key yomei@192.168.6.14 \
    'powershell -ExecutionPolicy Bypass -File C:\prog\jwwin\decomp_box.ps1 -Shards 10'
sh tools/decomp_get.sh
# 25983 functions, 25921 decompiled (99.8%)
# 25983 functions -> 654 files
```

自動解析は**一度だけ**走らせてプロジェクトを残します。逆コンパイルは
`-process -noanalysis -readOnly` で同じプロジェクトを開き直すので、
何度やり直しても解析し直しになりません。

| | |
|---|---|
| `tools/analyze_box.bat` | Ghidra の自動解析（342 秒） |
| `tools/inventory_box.bat` | 全関数の棚卸し CSV |
| `tools/decomp_box.ps1` | `.text` を 10 分割して並列に逆コンパイル |
| `tools/ghidra_scripts/` | 上の 2 つが呼ぶ Ghidra スクリプト |

**原典を駆動するスクリプトは `tools/` にあります。**README と RESUME の
古い版は `tmp/jwdraw.ps1`・`tmp/bars.ps1` と書いていましたが、`tmp/` は
リポジトリに入らないので新しい環境ではそこがまるごと欠けます。いまは
`tools/jwdraw.ps1`・`tools/bars.ps1` が本体で、`tmp/` の同名は転送する
だけです。

## VM の走りを `&` で切り離さない（2026-09-26 にまた踏みました）

`sh sync.sh '...' > file 2>&1 &` のように手元のシェルで切り離すと、
**手元の側だけが終わり、VM の側は走り続けます**。次の `check.sh` は
`ld.exe: cannot open output file tests/fuzz_test.exe: Permission denied`
で落ちます —— 前の試験がまだその exe を掴んでいるからです。

* 切り離しは**道具側の仕組みに任せる**（手元の `&` を使わない）
* 詰まったら、まず VM 側を掃除する:

```sh
for n in fuzz_test.exe cmdfuzz_test.exe shot.exe bigcirc_test.exe          linewalk_test.exe clipwalk_test.exe pickwalk_test.exe; do
    taskkill //F //IM "$n" > /dev/null 2>&1 || true
done
```

`taskkill` は当たらないと 128 を返し、`grep` も当たらないと 1 を返すので、
`probe.sh` の中では `|| true` を付けないとそこで終わります。
