## 壊れたファイルを読ませる試験（`tests/fuzz_test.c`、入りました）

同梱の図面・図形と `decomp/res` の答え、それに DXF・SFC・JWC を、
**途中で切ったもの**（頭のあたりは 1 バイトずつ、あとは粗い刻みで）と
**1 バイトだけ別の値にしたもの**にして読ませます。読めなくて構いません
——**落ちないこと**と、**いつまでも回らないこと**だけを見ます
（1 回の読みが 1 秒を超えたら `BAD`）。537 個のファイルから
**95 万通り**を 25 秒ほどで。

**読んだものは 16 回に 1 回、6 通りすべてで書き戻します**
（.jww・図形・DXF・SFC・JWC・座標ファイル）。中身は何とも比べません
——比べる相手がないので。**落ちなければよい**という試験です。

**三つ見つかりました。**

1. **円弧の始点角を (-π, π] に入れる `while` が永久に回ります** ——
   2π ずつしか動かないので、壊れた double（1e300 など）では終わりません。
   20 分回っても終わらないところを gdb で覗いて `src/jww.c` の
   その行でした。**読み手が桁違いの角を弾く**ようにして
   （`±1e6` ラジアンの外は「ありえない角」）、同じ形の `while` が
   ある DXF・SFC の読み手にも範囲の条件を足しました。
2. **座標が 1e300 だと書き出しでスタックが壊れます。**書き手は座標を
   `%f` で 128〜256 バイトの配列に `sprintf` しますが、1e300 は
   **309 桁**です（`src/sfcwrite.c` の `xs`/`ys` から溢れて、
   同じ関数の `nfill` を書き換えていました）。読み手が `±1e12` の外の
   座標を弾くようにしました —— 紙の上のミリでそんな数はありません。
3. **図形 (.jws) を SFC で書き出すと落ちます。**`jw_str` が
   「プールが無い」を見ていませんでした。図形はプールを持たない
   （`jw_parse_jws` は名前を読まない）ので、レイヤグループの名前を
   訊いた瞬間に 0 番地を読みます。**移植の窓から .jws を開いて SFC で
   保存すると落ちる**、実際のバグです。

書き出し側には同じ形の `while` や `sprintf` がまだいくつもありますが、
読み手を通った値しか見ないので、入口で弾くほうを直しました ——
`jw_numbers_sane()`（`src/jww.c`）を DXF・SFC・JWC の読み手の最後でも
呼んでいます。

**4 つめ（数字ではなく文字）。**`src/sfcwrite.c` は文字要素の中身を
`sprintf` で **1,024 バイトのスタックの配列**に流し込みます。.jww の
文字はいくらでも長く持てるので、**5,000 文字の文字を 1 つ置いた図面を
SFC で書き出すと落ちます**。`sprintf(t, …)` を
`snprintf(t, sizeof t, …)` に直しました（原典と 1 バイト違わないのは
そのまま）。`tests/fuzz_test.c` の最後に**手で組んだ図面**
（5,000 文字の文字・5,000 文字のレイヤ名・±9e11 の線）を書き出す段を
足してあります —— 直す前はそこで落ちます。

**壊し方の種は `JW_FUZZ_SEED` で替えられます。**既定では毎回同じ
壊し方をします（見つかった不具合をもう一度見られるように）が、環境変数
を置くと別の 95 万通りになります。`2 3 5 11 13 17 19 23` の 8 通りを
VM で流して **`BAD` は 1 つも出ませんでした**（1 回 25 秒ほど、読めた
数は 227,661〜227,983 と種ごとに少し動きます）。check.sh が回すのは
既定の種だけです —— 長く回すのは手で。

### AddressSanitizer に読ませたら、読み手の穴が 2 つ出ました

`tests/fuzz_test.c` の頭に「これだけは自分では捕まえられない」と
書いてあったもの —— **malloc した塊の中には収まっているが、ファイルの
末尾は越えている読み**（塊はちょうどの長さで取ってあるので、隣の塊に
入り込む）—— を、とうとう捕まえました。

**w64devkit には libasan がありません**（`-fsanitize=address` は
`cannot find -lasan`、`undefined` も同じ）。けれど**emscripten の
clang にはあり**、この試験は Windows を一切使わない素の C なので、
**まるごと node 向けに組んで走らせられます**。`tools/asan.sh` が
それです。

出たのは 2 つ、どちらも**決まった長さの頭を、そこまで無いファイルに
対して読む**話でした。

1. **`src/sfcread.c` の字句解析**（`decomp/res/ellip.sfc` を 304 バイトで
   切ったとき）。`/*SXF` の直後で終わるファイルだと、空白を読み飛ばす
   輪を抜けた時点で `p == n` になり、次の `r->b[r->p] != '#'` が
   末尾の 1 つ先を読みます。逃がし記号を読み飛ばしたあとの
   引用符の確かめも同じでした。
   どちらにも境界の確かめを足しました。
2. **`src/jww.c` の `jw_parse_jws`**（`decomp/res/fig.jws` を 348 バイトで
   切ったとき）。頭の各欄は 0x15c（348）で終わるので、そこまで読めた
   ファイルは何も言われずに通り、**そのあと頭を 0x1c4（452）バイト
   まるごと `memcpy`** します。348〜451 バイトの図形ファイルで
   104 バイトを末尾の先から写していました。頭の途中で終わるファイルは
   断るようにしました。

**素の Windows 版では 787 万通り流しても出ません**（隣の塊に収まって
しまうので）。直したあとは同じ 198 ファイル・393,900 通りを
AddressSanitizer で流して**報告ゼロ**です。

**コマンド乱打のほうも同じ目で見ます。**`tools/asan.sh` は続けて
`tests/cmdfuzz_test.c` も AddressSanitizer で組み、種 3 通り×600 手を
図面ありと白紙から流します —— 読み手だけでなく、**コマンド・作図・
書き手まで 1 バイトずつ見張った**うえでの走りです。こちらは**報告
ゼロ**でした。深く回したほう（`scratchpad/csoak.sh`、種 24 通り×
2,500 手を図面ありと白紙で 48 回）も**0 件**です。

**同じ形をほかの読み手でも探しました。**2 つとも「**決まった長さの頭を、
そこまで無いファイルに対して読む**」形だったので、同じ書き方を
総当たりで見ています:

* `ar_raw()`（`src/jww.c`）は `a->o + n > a->n` で断り、**断ったときは
  `a->o` を進めません**。なので `.jww` 側の `d->nhead = a.o` は必ず
  ファイルの内側です。
* 位置を定数で飛ばしているのは `a.o = 0xc8` と `a.o = 0x1c4`（直した
  ほう）の 2 か所だけ。前者のあとは `ar_*` しか読まないので安全です。
* `src/jwcread.c` の `JWC_ELEM`（0x975）は入口で
  `if (n < JWC_ELEM ...)` と確かめています。
* `src/sfcread.c` は位置を代入せず、`r->p += 5` の前に
  `r->p + 5 > r->n` を見ています。

**つまりこの形はもう残っていません。**

### 未定義動作のほうも見たら、2 つ出ました

`tools/asan.sh` は続けて **`-fsanitize=undefined`** でも組んで流します。
こちらは止まらずに報告を吐くので、数を見ます。出たのは 2 つでした。

1. **`src/cp932.c` の `jw_from_utf16` が短整数を境目の合わない番地から
   読んでいました**（12 件）。`.jww` の文字列はファイルのどこに来るとも
   知れないので、`src/jww.c` の `pool_put` が渡す番地は**奇数のことも
   ある**のに、`(const unsigned short *)` に鋳直して `s[i]` で読んで
   いました。x86 も wasm も通してしまうので、サニタイザまで気付き
   ません。**受け口を `const void *` にして、1 単位ずつ写して**
   読むようにしました —— 出る命令は同じで、決まりのうえで正しく
   なります。
2. **`tests/cmdfuzz_test.c` の時計が溢れていました**（9 件）。
   `(clock() - t0) * 1000 / CLOCKS_PER_SEC` は、長く回して 210 万
   刻みを超えると掛け算が `int` に入りません。**「コマンドが帰って
   こない」の見張りが出鱈目な値を見ていた**わけです。`double` を
   通してから掛けるようにしました。

直したあとは**報告ゼロ**です。

見つけ方は入れ子の目印です。`app_paint` の中 → `ui_paint` の中 →
`paint_buttons` の中、と 3 回に分けて `MARK` を吐かせて追い込みました

犯人は **`src/ui.c` の `checker()`** —— 押されたボタンの面に敷く

`ui.c` でそうなっているのはここだけです。道具の並びは 1264 画素幅の

### 道具を通しで走らせたら、さらに 3 つ

`tools/asan.sh` を 6 段そろえて最後まで走らせたら、**狭く試していた

1. **`src/sfcwrite.c` で筆 10 を 2 か所**。入口の守りが

2. **`src/coord.c` の `pen_w()` で int に入らない double**。

   来るので、壊れたファイルでは 1.8e10 になります。**int に入らない
   double を int にするのは未定義**です。上下で止めるようにしました。

（3 つ目は 1 の 2 か所目です。）

**この 3 つは、試験の段を全部そろえて初めて出ました。**読み手だけ、

### ブラウザが呼ぶ入口は、誰も叩いていませんでした

試験はどれも `app_*` をじかに叩きます。つまり **`src/main_wasm.c`
そのもの**（IME から来る UTF-16 と、見出しに入るファイル名）は、
**描かせる以外に通る道がありませんでした**。読んでみたら 1 つ出ました。

`jw_from_utf16()` は `cp932.h` に書いてあるとおり**「収まったぶん」では
なく「要るぶん」を返します**。`jw_key_u()` も `jw_text_in()` も
`i < sizeof buf` で守っていますが、**`jw_name()` は素通し**でした:

    char buf[128];
    long m = jw_from_utf16(s, n, buf, sizeof buf - 1);
    if (m < 0) m = 0;
    buf[m] = 0;                 /* m は 127 を超えうる */

ページは**開いたファイルの名前をそのまま**渡すので、長い名前で
**128 バイトの枠の外に NUL を書きます**。上下で止めるようにしました。

**入口を叩く試験も足しました** —— `node tests/wasm_check.js --api`
（`check.sh` に入れてあります）。長い名前・IME の 1 単位（サロゲートの
端や 0 を含む）・屑を読み手に、を通します。

**歯があることも確かめました。**`src/main_wasm.c` の守りを外して
AddressSanitizer 付きの wasm を組むと、**試験は止まります**。
ここで 1 つ学びました —— **400 文字の名前では捕まりません**。
`m` が 800 になり、128 バイトの枠の 670 バイト先は**赤い帯を飛び越えて
生きているスタック**なので、サニタイザは何も言いません。
**70 文字**なら `m` が 140、枠の 12 バイト先＝赤い帯の中で、そこで
止まります。試験には**両方**入れてあります。

（`tests/wasm_check.js` は `JW_WASM` で別の組み方の module を読めます。
サニタイザ付きのものを読ませるのに使いました。）

**同じ形をほかでも探しました。**`jw_from_utf16()`／`jw_to_utf16()` の
戻り値を添字に使っているところを総当たりで見ると、`src/jwwrite.c` は
その数だけ確保してから書いており、`src/main_win32.c` の `wide()` は
`out[n < cap - 1 ? n : cap - 1] = 0` と**ちゃんと止めています**
——`jw_name()` に足りなかったのはこれです。固定の枠に変数の添字で
NUL を置いているところも一通り見ましたが、`src/coord.c` は
`n < cap - 1` で、`src/cmd.c` の打ち込み欄は枠の 2 つ手前で止めており、
**ほかに同じ形はありません**。DXF の読み手（`line()`・`copy_name()`・
文字の組み立て 2 か所）もどれも `sizeof - 1` で止まっています。

### 種を 20 通りにしたら、書き手がスタックに溢れていました

**10 個目、そしてこれまでで一番重いもの。**`tools/asan.sh` は壊れた
ファイルの試験を**既定の種 1 つ**でしか回していませんでした —— 素の
Windows 版は 20 種で 787 万通り流してあるのに、**1 バイトずつ見張った
ほうは 39 万通りだけ**です。20 種に広げたら、**4 種で
stack-buffer-overflow の書き込み**が出ました。

    ==42==ERROR: AddressSanitizer: stack-buffer-overflow
    WRITE of size 9
        #1 __fwritex   #2 out   #3 fmt_fp   #4 printf_core

`fmt_fp` は C ライブラリが**浮動小数を書式化する**ところです。つまり
`sprintf` の宛先が足りていません。犯人は `src/sfcwrite.c` の
`ang()` —— 角を「常に 16 文字」に整える助け手:

    int whole = (int)fabs(v);   /* 1e300 を int に……未定義 */
    while (whole >= 10) { whole /= 10; digits++; }
    p = 15 - digits;
    if (p < 0) p = 0;
    sprintf(t, "%.*f", p, v);   /* t は 32 バイト */

`%.15g` なら何を渡しても 25 文字ほどですが、**`%f` は値で伸びます**。
壊れたファイルが持てる 1e300 は `%.0f` でも **301 文字**。それを
`char t[1024], a[32], b[32], c[32];` の **32 バイトの枠**に書いて
いました。桁数を数える `(int)fabs(v)` 自体も、入らない `double` を
`int` にする未定義動作です。

同じ形が 2 つありました。どちらも座標を `%.6f` で並べるところです:

* 弦の両端を `sprintf(xs, "(%.6f,%.6f)", …)` —— `xs` は 256 バイト、
  1e300 が 2 つなら 600 文字を超えます。
* ソリッドの隅 5 つを `nx += sprintf(xs + nx, …)` と**継ぎ足す**輪
  —— 残りを見ていませんでした。

3 か所とも `snprintf` と残り容量で止め、桁数の勘定は `double` のまま
にしました。**`.jws`・DXF・SFC・JWC のどれを読んでも SFC で書き出せる**
ので、これは壊れたファイル 1 つで踏めます。

**同じ形を総当たりしたら、あと 4 つ出ました。**見分け方は
**`%f` か `%g` か**です —— `%.15g` は何を渡しても 25 文字ほどで
収まりますが、`%f` は**値の大きさだけ伸びます**。固定の枠に `%f` で
書いているところを全部当たると:

| どこ | 枠 | 何の数 |
|---|---:|---|
| `src/app.c` の `moji_box` ×3 | 16 | 文字種の幅・高さ・間隔 |
| `src/cmd.c` の `sunpo_text` | 64 | 日影の数値（`mm * scale`） |
| `src/ui.c` の `mj_row` | 80 | 文字種一覧の 1 行（`%f` が 3 つ） |
| `src/ui.c` の文字種の入力欄 ×2 | 80 | 同上 |

どれも**図面から来る数**で、壊れた `.jww` なら 1e300 を持てます。
`mj_row` は呼び手の枠を知らなかったので、大きさを渡すようにしました。

**なぜこの 4 つが生き延びたか。**壊れたファイルの試験は
**読んで書くだけで、一度も描いていません**でした。これらの数が
文字になるのは `src/ui.c` と `src/draw.c`、つまり**画面側**です。
`tests/fuzz_test.c` に、読めた図面を **512 個に 1 つ、320×240 で
実際に描く**段を足しました（描くのは読むよりずっと遅いので間引いて
います）。

### SFC から来た角は、`.jww` の往復で一度だけ正規化されます

コマンド乱打を 4 形式に広げたら、`geo.sfc` と `sfcw6.sfc` で
`round_trip()` が鳴りました —— **`.jww` に書いて読み戻してもう一度
書くと、バイトが違う**。食い違う 8 バイトを `double` として読むと:

| | 1 回目 | 2 回目 |
|---|---|---|
| `geo.sfc` | 4.712389（3π/2） | −1.570796（−π/2） |
| `sfcw6.sfc` | 5.90236 | −0.38083（＝ 5.90236 − 2π） |

**同じ角を 2π ずらしただけ**です。どちらの側も正しい:

* `src/sfcread.c` は**始点角をそのまま**持ちます ——
  「*an arc that starts at 270 stays at 270, unlike one read from a DXF*」。
  原典の答えと突き合わせ済みで、これが原典の振る舞いです。
* `src/jww.c` の読み手は始点角を **(−π, π] に正規化**します。
  これも原典どおり（`o->d[3] -= 2π` の輪）。

つまり**移植の不具合ではなく**、原典自身の筋です。確かめたのは
**落ち着くかどうか**で、答えは落ち着く:

    geo.sfc     1st=17064 2nd=17064 3rd=17064   1対2 違う / 2対3 同じ
    sfcw6.sfc   1st=128499 …                    1対2 違う / 2対3 同じ

一度きりの正規化で、失われているものはありません。`round_trip()` の
条件を**「すぐ一致するか、もう 1 周で落ち着くか」**に直しました ——
文字形式に `settles()` が課しているのと同じ規則です。動き続けるなら
やはり `BAD` になります。

### 形式をまたいで続けて読むと、色の表からはみ出していました

**9 つ目**。DXF も SFC も JWC も「いま開いているものの**中へ**」読みます。
つまり**前の読み手が残したものが次の読み手の出発点**です。ところが
試験はどれも**読み手に 1 ファイル渡して、また最初から**なので、この継ぎ目
だけ誰も見ていませんでした。読んでみたら穴がありました。

図面が持てる任意色は **257 個**（`xcolor[257]`）。SFC は
**259 個**まで名乗れます（`NCOL` は 260、守りは `ncolour < NCOL - 1`）。
`src/sfcread.c` は書き戻しの輪を `i <= 256` でちゃんと止めているのに、
**個数 `xcolor_n` だけ素通し**でした:

    for (i = 1; i <= r->ncolour && i <= 256; i++) { … }   /* 止めている */
    if (r->ncolour > d->xcolor_n)
        d->xcolor_n = r->ncolour;                         /* 止めていない */

そして `src/dxfread.c` はその個数を `ncol = 100 + xcolor_n` として
**`col[357]` の添字の上限**に使い、`col[1 .. ncol]` を舐めます。
**256 色より多い SFC を開いてから DXF を開く**と、表の外を読みます。

**抜け道はここだけ**でした。`.jww` 側の個数は `i < 0x101` の輪から
決まるので 256 に収まり、`dxfread` 自身も `r->ncol < 356` で止めて
います。`sfcread` のここだけが上限を超えられました。

**取り方**（`scratchpad/ncol.c`）: 同梱の SFC に
`user_defined_colour_feature` を 300 個足して読ませ、続けて DXF を読ませる。

| | `xcolor_n` | |
|---|---:|---|
| 上限を入れたあと | 256 | 報告なし |
| 上限なし | **259** | `src/dxfread.c:186: index 357 out of bounds for type 'unsigned int[357]'` |

**AddressSanitizer では出ません。**`col[357]` は構造体の途中の配列なので、
2 つ先は**同じ構造体の別の欄**に落ち、赤い帯に当たらないからです。
これを見るのは**未定義動作のほうの配列境界**の検査 —— 筆 10 の
`print_rgb[10]` を捕まえたのと同じものです。落ちる類ではなく、
**別の欄を色として読んで「近い色」の選び方が狂う**という不具合です。

**継ぎ目を見る試験も足しました** —— `tests/seq_test.c`
（`check.sh` から呼びます）。4 形式の**順序対 16 通り**を 1 つの図面に

### 紙のミリを画素に直すところを 1 か所にまとめました（2026-09-26）

**`(int)` そのものが未定義になります。**double を int に直す式は、値が
int に収まらないと**動作未定義**です。`jw_numbers_sane()` は座標を
±1e12 まで通し、用紙に合わせた表示は 1 画素あたり 0.5 mm ほどなので、
**壊れていない読み方でも 2e12 が来ます**。`src/coord.c` の線幅で 1 度
直した穴と同じものが、画面に出す側の至るところにありました。

`src/view.h` に `jw_px_round()` を置いて、**±1e8 で止めてから**直します。
1 億画素は 10 万画面ぶん先なので、見えるものは何も変わりません。
±1e8 にしたのは**2 つ引いても int を溢れさせない**ためです。
`!(p > lo)` と書いてあるのは、NaN がどの比較にも負けて最初の枝に
落ちるようにするためです。

通したのは `jw_sx`・`jw_sy`（移植のいちばん熱い 2 つ）と、円弧の半径
2 か所、文字の 1 文字の刻み 2 か所、拾い上げの距離、目盛の格子、
塗りつぶしの走査線、最後の弦の点。

**そのうえで 3 つ、素直に壊れるところが出ました。**

**1. 円の四分円の表が半径 5,792 から溢れます。**半径 256 までは
`src/gen/circle.h` に GDI の歩き方が入っていますが、その先は中点円を
歩きます。中点円は**半径より多く点を出します**（およそ √2 倍）。
四分円の置き場は `ARC_MAX / 8` = 8,192 で、半径の門は
`ARC_MAX / 8 - 2` = 8,190。**5,792 から 8,189 までは素通りして
その先に書いていました。**どの図面でも**拡大していけば届きます**。
置き場を `ARC_MAX / 4` に広げました（静的に 256KB）。

直す前のものを ASan 付きで組むと、こう言ってきます
（`sh tools/asanone.sh bigcirc_test`、半径 5,793 の行で）:

    ==42==ERROR: AddressSanitizer: memcpy-param-overlap:
      memory ranges [0x24af8140,0x24afc144) and [0x24af4140,0x24af8144) overlap
      #1 jw_draw
      0x24af8140 is located 16384 bytes inside of global variable
      'circle_points.qxs' defined in 'src/draw.c' of size 65536

**最初に出るのは配列の外ではなく、隣の四分円との重なりです。**
`qxs` は `[4][8192]` の一枚板なので、四分円 0 の歩きが 8,192 を越えると
四分円 1 の場所に書き、その 4 つを配る `memcpy` が自分自身と重なります。
最後の四分円まで行くと板の外に出ます（半径 8,189 なら 3,388 個ぶん、
`qys` の中へ）。直したものは `CLEAN` です。
同じ歩き出しで `2 * rp^3` を `long` に入れていましたが、`long` は
Windows でも wasm でも 32 ビットなので**半径 1,291 で溢れます**。
double にしました（どれも 2^53 未満の整数なので値は変わりません）。
`tests/bigcirc_test.c` が半径 255〜1e15 で通します。

**2. 窓から遠い線が 2 億歩あるきます。**`line()` の切り取りは**長いほうの
軸にしか効きません**。用紙の 100 万画素上を走る水平線は、横は窓の中に
収まったまま縦だけ遠くにある状態でここに来ます。画素ごとの歩きは
**短いほうの軸が画素で長ければそちらを刻む**ので、2 億歩、全部
`put()` に捨てられます。窓から 64 画素より外に両端があるものは
その場で捨てます（いちばん太いペンが 16 画素なので 64 で足ります）。

**3. 目盛が返ってこないことがあります。**`mesh_min <= 0` と
`mesh_ix = 1e-300` の図面（壊れた読みで出ます）だと、門
`mesh_ix / mmpp >= mesh_min` を通ってしまい、窓の幅を 1e-300 mm 刻みで
歩きます。**1 画素以上**という条件を足しました。実在の図面はどれも
15 なので何も変わりません。文字も同じで、1 文字が 1e12 mm の書式だと
刻みが 1 億×1 億になるので、**画面の幅＋高さで止めます**（1 画素に
1 点あれば隙間は空きません）。

`app_zoom` も、倍率を掛け続けて `mmpp` が double の外に出ると
**そのあとの座標が全部 NaN** になるので、範囲を出る一歩は断ります。
画面倍率の表示（`src/ui.c`）の `(long)` も同じ手当てです。

**どれも先にサニタイザが言ってきたものではありません** —— 原を読んで
見つけました。1 番だけは `tests/bigcirc_test.c` を足したあとで
サニタイザに確かめさせてあります（上の控え）。2 番と 3 番、それに
`(int)` の手当ては、壊れたファイルの掃き出しが**まだ踏んでいない**
だけで、踏めば止まるところです。

**1 つだけ道具が増えました。**`tools/asanone.sh` は試験を 1 本だけ
サニタイザ付きで組んで走らせます。`tools/asan.sh` は 6 段で何時間も
かかるので、直したところを確かめるにはこちらを使います。

直したあとの `sh tools/asan.sh` は 4 段とも報告ゼロです —— 読み手
（壊れた 39 万件）・コマンド乱打・未定義動作・**同梱 16 枚を 1×1 から
2000×1200 までの窓で描く段**。採点は 814 画素のまま、`check.sh` は
1,267 項目 ok なので、**±1e8 で止めても見えるものは何も変わっていません**。

### 乱打の絵を拡大しても描くようにしました（2026-09-26）

`tests/fuzz_test.c` は 512 件に 1 件を 320×240 で描きますが、**用紙を
窓に合わせた倍率だけ**でした。合わせた倍率は図面が何と言っていても
1 画素あたり 0.5 mm ほどなので、**窓より大きい円は一度も来ません**。
上の 1 番（四分円の置き場）は半径 5,792 から 8,189 の帯でだけ起きるので、
**この網では永久に捕まりません**でした。

描いたあと **8 回拡大して、そのたびに描く**ようにしました。倍率は
固定ではなく 1.5〜5.4 から引きます —— 切り詰めの格子と同じ理由で、
固定だとどの図面も同じ半径の並びにしか当たらず、この帯は 1.4 倍しか
幅がありません。

**それでも、この網はあの溢れを捕まえません。**直しを抜いた原で
198 個・39 万 3,800 通りを ASan 付きで通してみたら、**報告ゼロ**でした。
理由は**拡大すると円の中心が画面から出る**からです —— GDI の環に
行くのは中心が画面の中にいるあいだだけなので、半径が育つ前に候補が
消えます。拡大は描く段を広げはしますが、**半径の帯を狙う網ではない**
ということです。

そこで `tests/bigcirc_test.c` のほうで**半径 1 から 8,200 まで
全部**（真円と部分円の両方）歩かせることにしました。`circle_points` が
諦める `ARC_MAX/8 - 2` までが定義域そのものなので、当てずっぽうに
探すより**端から端まで通したほうが早い**（ネイティブで 1 秒ほど）。

### 角度を 1 周ずつ畳む輪が、返ってこないことがあります（2026-09-26）

書き手はどれも角度を**1 周ずつ足し引きして**0〜360 に入れます。原典が
そうしているからで、最下位ビットまで合わせるにはこう書くしかありません:

5.7e13 度なので、この輪は**1,600 億回**まわります。1 回 1 ナノ秒でも
160 秒、要素ごとに。返ってこないのと同じです。

`src/jww.h` に `jw_prefold(v, 周期)` を置きました。**100 万を超える
ぶんだけ `fmod` で落とし、それ以下は素通し**です。実在の図面の角度は
どれも 100 万よりずっと小さいので、**輪はこれまでどおりまわり、
出るバイトも同じ**です。

通した先:

| | |
|---|---|
| `src/draw.c` | 環の画素を角度で選ぶところ（始点と終点、各 1 回。中の輪は最大 4 万 6 千画素ぶんまわります） |
| `src/dxf.c` | 円弧の 2 つの端 |
| `src/sfcwrite.c` | 7 か所（円弧・楕円弧の端と傾き） |
| `src/jwcwrite.c` | `deg()` |

**SEEDBAD も SEEDROOM も 0 件**です。所要 57 分。

**3 つずつ同時に流します**（`JW_SEED_JOBS`、既定 3）。ビルド箱は 4 コア
14 GB で、サニタイザ付きの 1 本が 2 GB ほど持つので 3 本は余裕で入ります。
組んだ `fuzz.js` は共有で構いません —— 走っているあいだ誰も書きません。
出力だけ種ごとに分け、**1 組終わるごとに種の順に**まとめて言います
（読む側が進み具合を掴めるように）。1 本ずつだと 20 種で 2 時間半、
3 本ずつなら 1 時間ほどです。

## 手当たり次第にコマンドを叩く試験（`tests/cmdfuzz_test.c`、入りました）

ほかの試験は**コマンドを 1 つずつ、人が使うとおりに**駆動します。
これは**誰もやらない順番で全部**叩きます —— 同梱の図面を開いたうえで、
ツールバーのコマンド 70 個・窓のどこでも左右クリック・文字キー・
再描画を、決まった擬似乱数の列で混ぜて延々と。何とも比べません
（比べる相手がない）。見るのは 3 つだけ:

* **落ちないか**
* **図面が「図面がありえない数」を持たないか**（`jw_numbers_sane()`、
  読み手と同じ門）
* **残ったものを 6 通りとも書き出せるか**
* **書いて・読み戻して・また書いたら同じバイトか**（`round_trip()`）
  —— 手当たり次第に編集した図面は、どのファイルにも無い形を持ちます。
  比べる相手が無くても**これだけは言えます**: 2 回目の書き出しが違えば、
  書き手が読み手の取らないものを置いたか、読み手が落としたかのどちらかです。
* **DXF・SFC・JWC は「1 往復したら落ち着くか」**（`settles()`）——
  この 3 つは .jww の持ち物を全部は運べないので、1 回目と 2 回目が
  違うのは当たり前です。**2 回目と 3 回目**が同じでなければなりません。
  行ごとに見て、**両方が数字の行だけは最後の桁の揺れを許します**
  —— 座標は倍率を掛けて出て割って戻るので、同じビット列には戻りません
  （`Test1` の DXF で `10258.206194982036` が `…034` に）。
  見たいのは**消えた行・変わった行・増えた行**のほうです。

  **JWC には中身が生のバイトの行があります。**`円地図.jww` を手当たり
  次第に編集したものを JWC で書くと、`5c 03 44 1c 37 fe 43 …` と続く
  2,665 バイトの行が出ます（`\` で始まる記録の中に座標が詰まっている）。
  そこも座標は倍率を掛けて出て割って戻るので最後のビットが動きます。
  **行の中に制御文字があれば長さだけを見る**ようにしてあります。

  **DXF は外してあります —— 原典自身が落ち着かないからです。**
  レイヤ名は DXF に `_<グループ>-<レイヤ>_<名前>` の形で入り、読み戻すと
  **その全部が名前になります**（`tests/dxfread_test.c` が移植のレイヤ名を
  原典のものと突き合わせていて、一致します —— つまり原典がそうします）。
  なので次に書くと `_0-a__0-a_東壁日影` になり、その次はもう 1 つ増えます。
  名前が変わると LAYER の表の中身が変わり、**要素の乗るレイヤまで動きます**
  （`_0-d_ADD_LINE` が `_0-e_ADD_LINE` になる）。**Jw_cad で DXF を
  開いて保存して開いて保存すると、レイヤ名が伸びてレイヤがずれていく**、
  ということです。移植の落ち度ではないので、落ち着きを要求するのは
  SFC と JWC だけにしました。

  **読み手は「いまの図面に読み込む」ことに注意**（原典の 読込 と同じで、
  用紙・ペン・レイヤ名はそのままで要素だけ入れ替わります）。この試験も
  世代ごとに**新規の白紙から**始めます —— ゼロで埋めた構造体から始めると
  用紙が 0 mm になり、`$EXTMAX` が 0 になって落ち着きません。

種は `JW_CMDFUZZ_SEED`、長さは `JW_CMDFUZZ_STEPS`（既定 600）。
check.sh は `Test1`・`Test5`・`Test7` を既定の種で叩き、そのあと
**何も開かずに**（`app_new()` の白紙から）もう一度叩きます —— 最初の
要素を作るコマンドは、下に何も無いときの筋が別なので。

**長く回した分**: 種 16 通り（2〜53）で、同梱の図面 16 枚に
2,500〜4,000 手ずつ、白紙にも 8,000 手ずつ —— 合わせて **144 万手**を
VM で流して、**落ちたものも、数の壊れたものも、書き出せなかったものも、
