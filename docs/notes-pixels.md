## 円ソリッドの書き出し（入っています、3 形式とも 1 バイト違わず）

原典に `decomp/res/hatin.jww`（DXF 読み込みで作った、平らなソリッド 3 つと
円ソリッド 2 つの図）を書かせたものが `decomp/res/rsolid.dxf` /
`.sfc` / `.jwc` です。`tools/refanswers.sh` の `=== rsolid` が作ります。

**円ソリッドは「弓形」で、扇形ではありません。** 45°→270° の円ソリッドの
輪郭を、原典は SFC に「弧 + 両端を結ぶ 1 本の弦」として書きます —— 中心へ
戻る 2 本の半径ではありません。`src/draw.c` の `round_solid()` も中心を
打たずに閉じるようにしました（画面の画素そのものは、いま原典の
スクリーンショットが撮れない環境なので突き合わせていません）。

形式ごとの書き方:

* **DXF** —— 塗りは落とし、縁だけを書きます。一周なら `CIRCLE`、一部なら
  `ARC`。弦は書きません。
* **SFC** —— 輪郭 + `composite_curve_org_feature(色,線種,太さ,'1')`、
  そしてその図形層の要素をすべて書いたあとに、ソリッド 1 つにつき
  `fill_area_style_colour_feature(層,色,何番目の複合曲線か,'0','()')` を
  1 行。これだけが「塗ってある」と言っている唯一のものです。
  一周の円ソリッドは `arc_feature` 2 本（s0→s0+180 と s0+180→s0）に
  割れます。一部なら弧 1 本 + 終わりから始まりへ戻る 2 点の
  `polyline_feature`。
  平らなソリッドは 5 点の閉じた `polyline_feature` で、頂点の順は
  **c0, c3, c2, c1, c0**（後ろ 3 つが逆）。
* **JWC** —— 円弧のレコードが 1 つだけ。弦も書きません。

`src/jww.c` の `jw_round_solid()` が、線種 101 のソリッドを CDataEnko の
形（中心・半径・始まり・振り・傾き・扁平）に詰め替えます。3 つの書き出しは
これを通して円弧として書いています。

## 点線が自分の端をはみ出していました（直しました、72 画素）

`tools/why.py` で `天空率表` の残り 41 画素を並べたら、11 個ずつ 2 列に
きれいに並ぶ画素が出ました。`WHY_BOX` で絵にすると——

      546 ........O................................O...............................O..
      547 ........O................................O...............................O..
      548 ############################################################################

`#` は両方が打った線、`O` は**移植だけが打った**画素です。その x は
`seg 478 493 548 493 638 9` —— **y=548 から下へ伸びる補助線**の x でした。
移植はその**上に 2 画素**はみ出していたわけです。

`src/draw.c` の線種の輪は

    nbits = (int)(major / ppb) + 2;
    for (i = 0; i <= nbits; ) { … }

と**端の 2 ビットぶん余分に**回ります。`bm` は端で頭打ちにしますが、
`am`（run の始まり）が**すでに端を越えている**と、そこから端まで戻る
線を引いてしまいます。原典の `FUN_004bbef0` は
**「切り捨てた位置が端よりまだ手前のあいだ」歩く**ので、そこで止まります
（移植は円弧の弦のときだけその条件を見ていました）。**線のときも見る**
ようにしました。

**15 枚の合計が 916 → 844。**6 枚が良くなり、悪くなったものはありません
（`天空率表` 41 → 13、`サンプル` 103 → 81、`Test6` 44 → 33、
`Ａマンション平面例` 410 → 401、`木造平面例` 23 → 21）。

## 残りの 1 画素ずれ —— 直線ではなく円弧のほうでした

**直線のラスタライズは GDI と完全に一致しています。**`tmp/gdiline.c`
（`src/draw.c` を `-Dstatic=` で開いて `line()` を直に呼ぶもの）で、
端点の差が ±40 の**全 6,560 通り**を GDI の `MoveTo`/`LineTo` と
突き合わせて、**1 画素も違いませんでした**。だから残差は「線の歩き方」
ではありません。

`Ａマンション平面例.jww` の残りを 1 つ追いかけると、**円弧の環が
1 画素ぶん小さい**のが出てきました。要素 1656（中心 543,340 の
90 度の弧、半径 10.2 mm）は

* 移植: `rp = (int)(10.2 / 0.432945 + 0.5) = 24`
* 原典: 環は **25** の上に乗っています（`tmp/arcfit.exe 25 1` の環に
  基準画像の画素が乗り、24 には乗りません）

中心は同じです（中心を 1 つずらした 24 の環でも近い当たりになるので、
そこは決めきれていません）。ただし**半径の丸めそのものは合っています**
—— `rp` を一律に +1 すると 15 枚の合計が 974 → 7,308 に跳ね上がります。

### `Test6` の線は、原典のほうが 1 画素長く始まります（未解決）

`tools/why.py` で `Test6` の残り 33 画素を見ると、**27 画素が原典だけ**が
打ったもので、どれも**横線の左端の 1 つ外**です。

    seg 52 309 712 334 712   （実線）
    seg 82 309 711 334 711

    711 ........T############
    712 ........T############   ← T は原典だけ、列 8 は x=308

`JW_SHOT_ELEMS` の書き出しに**丸める前の位置**も入れました。この線の
左端は **308.58** です。移植は `jw_sx` で 309 にします（`(int)` は
0 方向への切り捨てで、この点は留め画素より左なので **上に**丸まる）。
原典は 308 に打っています。

**「0 方向ではなく下方向に丸める」ではありません。**0 方向への切り捨てで
合っています —— ただし**最初の測り方は間違っていました**。`by − (int)(w)`
の `w` を `floor` すると画面の y は**逆に上へ**丸まります。正しく測り
直した表は下の「`Test6` の壁は、青い線が 1 画素左から始まります」に
あります（x だけ `floor` で 5,043、y を画面下方向で 4,350、両方で 6,980）。

**x=308 には要素がありません**（seg も点もソリッドも）。広く絵にしても
その 2 本きりの、宙に浮いた 2 画素幅の壁です:

    711 ............T##########################......
    712 ............T##########################......

**原典の打った幅は 308〜334、移植は 309〜334。**丸める前は
**308.58〜333.08** なので、原典は**その線分が掠める画素を全部**
（`floor(左)`〜`ceil(右)`）打っていることになります。移植は両端とも
0 方向へ切り捨てて 309〜334。

**両端とも floor にするのは駄目**（上記 149,336）なので、
「左は floor、右は ceil」という**外向きの丸め**に見えます。
**それも測りました —— 駄目です**（`JW_LINE_OUT=1` で 15 枚が
130,407 画素、下の「『外向きに丸める』を測りました」）。ここは未解決です。
`Test6` は包絡処理のかかった図面なので、壁の端の始末という線もあります。

### `Test7` に残る 3 画素は、画面から出る点線です

`tools/why.py` にかけると 3 つとも**直線の上**（移植が 2、原典が 1）で、
どれも**線種 2 の点線**、しかも**画布の外まで伸びている**ものでした。

    seg 30  544,481 -> -678,218   ltype 2
    seg 80  429,610 ->  544,402   ltype 2
    seg 29 -429,332 ->  792,595   ltype 2

30 と 29 は長いほうの軸で画面から出るので、`src/draw.c` の `line()` が
**端を入れ替えてから切り取り**ます（下の「線を切り取る向き」）。
80 は出ないので入れ替えません。**点線の模様は端から始まる**ので、
残る 3 画素は「切り取ったあとの模様の位置」の端数だと思われます。
模様は「repeat がちょうど収まるように伸ばす」ので、その数の数え方の
端数です。**数え方は 4 通り試して、いまのが断然よい**と分かりました
（`reps = (int)(斜辺の長さ / (unit * ppb))`）——

    いまのまま（斜辺・切り捨て）       916
    長いほうの軸・切り捨て           7,960
    斜辺・四捨五入                   9,378
    長いほうの軸・四捨五入          12,682

なので端数の出どころは別のところです。3 画素なのでそれ以上は
追いかけていませんが、`Test7` を 0 にするならここです。

### 要素ごとの線幅（`+0x2c`）は印刷のほうの話でした

`src/jww.c` は要素の `+0x2c` を `o->width` として読みますが、
`src/draw.c` はそれを使わず、色から引いた `pen_width[]` で描きます。
使わなくてよい、と確かめました —— `FUN_00421490` の頭（21531 行）と
線のほう（22563 行）に

    if ((param_3 != 0) && (DAT_00a0cae8 != 0) && (…)) {
        幅 = 要素の +0x2c があればそれ / 100 ミリ、
             無ければ doc+0x68c0 の色ごとのミリ
        … FUN_0044f7c0(…, 幅);          /* 太い線で描く */
        if (DAT_00a0cae8 < 100) return;  /* ここで終わり */
    }

という枝があります。**`param_3` が非 0 のとき**にしか入りません。
すぐ上で `if ((param_3 != 0) && (DAT_00a0b43c != 0)) local_dc = DAT_00a0b440;`
と DC を差し替えているので、**`param_3` は印刷（またはプレビュー）側の
もの**です。画面では通りません。`doc+0x68c0` は**色ごとの線幅をミリで
持つ 10 個の表**（`src/jww.c` が `print_width[]` として読んでいるもの）。

### 残った画素がどの要素のものかを言う道具（`tools/why.py`）

採点は「何画素違う」までしか言いません。**どの要素の、どのあたりか**を
言わせるために `tools/why.py` を足しました。`tests/shot.exe` に
`JW_SHOT_ELEMS=1` を渡すと `<出力>.elems` に要素の落ちた場所を画素で
書き出すので、それと基準画像を突き合わせて、違う画素 1 つずつを

* **円弧の端**（環の上、端から 3 画素以内）
* **円弧の途中**
* **円弧の環の上だが掃引の外**
* **直線の上**
* **点の上・ソリッドの中**
* **どれの上でもない**

に分け、**移植が打ったもの／原典が打ったもの**の別と、いちばん悪い
円弧の一覧まで出します。使い方は

    sh tools/score.sh                      # tests/shot.exe を作る
    JW_SHOT_ELEMS=1 ./tests/shot.exe tmp/d14.out.png tmp/d14.jww
    python tools/why.py tmp/refs/d14.png tmp/d14.out.png
    python tools/arcrp.py tmp/refs/d14.png tmp/d14.out.png

    tmp/d14.out.png: 410 wrong pixels outside the text
                               all    ours  theirs
      arc end                  104      49      55  (25.4%)
      arc middle               131      62      69  (32.0%)
      arc outside the sweep    156      81      75  (38.0%)
      line                      14      14       0  ( 3.4%)
      nothing                    5       0       5  ( 1.2%)

**どの組も「移植が打った」と「原典が打った」がほぼ半々**です ——
つまり**環が 1 画素ずれている**のであって、線が足りない・余計なのでは
ありません。`日影図` にいたっては **275 画素のうち 223 画素が要素 1 つ**、
中心 (1009,120)・半径 25 mm（57.7441 画素）・掃引ちょうど 2π・実線・
線幅 1 の**真円 1 つ**です。**ただし `日影図` は同心円が何重にも重なった
図**なので、「この画素はどの円のものか」の割り当て自体が当てになりません
—— 差の画素を並べると「原典の環は中心が半画素右下」に見えますが、
実際に真円の環を右下に半画素ずらして採点すると 275 → **292**（15 枚では
973 → 4,845、`天空率表` が 98 → 3,901）で**悪くなります**。近くの別の
円の画素を拾っていた、ということです。**同心円の図では `tools/why.py`
の割り当てを信用しないこと。**

**枠の偶奇ではありません。**真円を（部分円弧と同じ）2r+1 の枠に入れて
みると、`日影図` は 275 → 256 としか動かず、`天空率表` が 98 → **2,547**、
15 枚の合計は 973 → 3,483 に跳ねます。**線幅でもありません**（15 枚とも
ペンは全部 1）。

### 原典の環は、いくつかの円弧で**半径がちょうど 1 画素大きい**

`WHY_ARC=1656 python tools/why.py tmp/refs/d14.png tmp/d14.out.png` で、その円弧の違う画素を中心からの
差で全部並べると、はっきりします。

    ours（移植が打った）              theirs（原典が打った）
       1  24  r=24.021                  0  25  r=25.000
       5  23  r=23.537                  7  24  r=25.000
      12  20  r=23.324                 15  20  r=25.000
      23   5  r=23.537                 25   2  r=25.080

**原典の環は半径ちょうど 25 の中点円**です（中心は移植と同じ画素）。
移植は `r/mmpp + 0.5 = 10.2/0.432945 + 0.5 = 24.06` から **24**。
原典は **25**。中心も掃引も合っていて、**半径だけが 1 画素大きい**。

`tools/arcrp.py` は、基準画像を円弧の角度に沿って
なぞって**原典が使った半径を測り直す**道具です。`Ａマンション平面例` で
はっきり測れた 26 本のうち 10 本が食い違い、**うち 3 本は
`+0x44` が `0x80` の円弧**（色 1・レイヤ 3・掃引 ±90 度・6 mm）で、
**3 本とも +1**。残りは同心の円弧が並んでいる階段状のところで、
測り直しのほうが隣の環に引っかかっているので当てになりません。

**なぜ 1 大きいのかは分かっていません。**分かっていることだけ:

* 枠の偶奇でも、線幅でも、GDI の `Arc` でもない（上記）。
* 中心の画素は合っている（差の並びが同心の環になる）。
* `r + 0.5 mm` で丸めると 6 本中 6 本合いますが、**0.5 mm がどこから
  来るのか説明がつきません**（`doc+0x1730` がペンの太さの表の 8 番目
  だとすればちょうど 0.5 mm ですが、同じ番地は `FUN_004b6d60` では
  倍率として使われていて、両立しません）。
* `+0x44` の `0x80` が効いているようにも見えますが、`0x10` の円弧は
  15 本が合って 7 本が合わないので、**旗だけでは決まりません**。

**原典の円そのものを測りました。**`tools/why.py` が、基準画像の
インクのうち移植の環の近くにあるものに**最小二乗で円を当てはめる**ように
なりました（代数的な当てはめ）。`日影図` の例の真円で——

| | 中心（移植の中心画素から） | 半径 |
|---|---|---|
| 移植（GDI の 2r の環） | −0.50, −0.50 | 58 |
| **原典のインクの当てはめ** | **−0.08, −0.04** | **57.79** |

つまり原典のその円は**中心画素のちょうど上に、丸めない半径
（`r/mmpp` = 57.7441）で**乗っています。GDI の環（半画素ずれて半径 58）
ではありません。試しに真円だけをそう描くと `日影図` は 275 → **151**、
`Ａマンション平面例` も 401 → **367** と良くなりますが、**`天空率表` が
13 → 3,220** と壊れます（合計 844 → 3,931）。**どの円がどちらなのかの
見分けがまだ付きません。**半径で分けようとしても駄目でした ——
「半径が 30・45・56 画素より大きい真円だけを真円にする」を試しても
`天空率表` は 13 → 1,699〜1,938 のままです（`日影図` は 151 になります）。
**`天空率表` には半径 56 画素より大きい真円があって、そちらは GDI の環に
乗っている**ということです。

**この 1 つの円について、潰した筋の一覧**（いずれも `日影図` の 275 は
ほとんど動かないか、他が壊れる）:

| 試したこと | 日影図 | 15 枚の合計 |
|---|---|---|
| いまのまま（GDI の 2r の環） | 275 | **814** |
| 2r+1 の枠（中心画素の上、半径 58） | 256 | 3,384 |
| 丸めない半径の真円（中心画素の上） | **151** | 3,931 |
| 同上、半径 30/45/56 画素より大きいものだけ | 151 | 2,406〜2,645 |
| 半径 5〜30 mm 超は折れ線 | 262〜275 | 2,613〜3,996 |
| GDI の `Arc` に丸投げ | —— | 820（他は良くなる） |

**「半径がこれより大きい円弧は折れ線」でもありません。**
`FUN_00421490` の `doc+0x1730 <= 半径` の枝を、しきい値を 5・10・15・
20・24・30 ミリと変えて試すと、15 枚の合計は 844 に対して
**2,613〜3,996** とどれも悪くなります（`日影図` の真円も 275 → 262 と
しか動きません）。画面の側でこの枝に入る円弧は、少なくともこの 15 枚には
ありません。

**真円の枠の偶奇でもありません**（もう一度、新しい表で試して）——
真円を 2r+1 の枠に入れると 844 → **3,384**、`日影図` は 275 → 256。

**「部分円弧はみな +1」ではありません。**試しに掃引が一周に満たない
円弧の半径を一律に 1 増やすと、15 枚の合計は 973 → **2,119**、
`Ａマンション平面例` 自身も 410 → 677 と悪くなります
（`サンプル` 103 → 461、`木造平面例` 23 → 319）。**一部の円弧だけ**が
1 大きい、という形です。

次に見るなら、`FUN_00421490` が `FUN_004b8250` を呼ぶ前に半径に何か
足していないか（`local_c4` の出どころ `obj+0x68` をもう一度）、
あるいは**建具・曲線属性の円弧を別の関数が描いていないか**です。

### GDI の `Arc` は GDI の `Ellipse` と別の環を描きます

移植の円弧は `src/gen/circle.h` の表を歩きます —— **GDI の `Ellipse` に
半径ごとに訊いて書き留めた環**です。ところが**`Arc` はその環の上を
通りません**。`tmp/arcvsell2.c`（GDI だけを使う 1 ファイルの試し。
`sh tmp/build_probe.sh arcvsell2 3 40`）で、半径 3〜40・端を 15 度刻みの
2 万通りに取って数えると——

    1,272,013 pixels drawn by Arc, 73,437 of them not on GDI's ellipse

それらしい差は見つかりませんでした。

**逆コンパイル出力の見落としを 1 つ直しました。**GDI に行くかどうかの
判定は 4 つではなく **5 つ**です（`all_00401000.c` 21910 行）:

    doc[0x1730] <= r                  ← これを見落としていました
    || cx <= doc[0x79f8] || doc[0x7a08] <= cx
    || cy <= doc[0x7a00] || doc[0x7a10] <= cy
    || 線種が実線でない … → 折れ線へ

**何も描かずに帰る**」（円が窓をすっぽり呑んでいる）という間引きが
あり、そこで同じ値を窓の差し渡しとして使っています。**半径が窓ほど
大きい円は GDI に渡さない**、という意味です。この 5 つ目はここの
15 枚では発火しません（どれも半径が窓よりずっと小さい）。

  ならず、ほかが軒並み壊れる

### 拾い上げも全画素で歩かせます（`tests/pickwalk_test.c`、2026-09-26）

どのコマンドも**拾い上げ**から始まります。`src/pick.c` がマウスに
いちばん近い要素を決めて `d->obj` の**添字**を返し、その添字はすぐ
そのまま使われます。**図面にない添字は要素の並びの外読み**ですが、
並びは 1 つの `malloc` なので、隣を指してもその中に落ちて
**サニタイザには映りません**（枠の切り取りと同じ形の穴）。

窓の**全画素**（縁の外 4 画素ぶんも）を、モード 4 通り × 同点の決め方
2 通りで押します。図面は 1 クラスずつ 13 個＋ブロックの定義。
**32,864 押し × 8 通り**、返る番号はどれも図面のもの、読み取り点
3,433 個はどれも数でした。倍率を 100 万分の 1 から 100 万倍まで振った
ものと、数が全部端にあるもの、空の図面、レイヤを消したものも。

**この網は 2 回すり抜けられました。**わざと 1 だけずらす細工を
`jw_pick_tie` に入れて確かめたところ:

1. **判定を `[0, nobj)` にしていた** —— 正しくは **`[0, ndrawn)`** です。
   ブロックの定義とその中身は同じ並びの `ndrawn` の**後ろ**に座って
   いるので、`nobj` で見ると**定義を返しても通ります**。コマンドが
   定義を渡されたら、定義そのものを編集してしまいます。
2. **最後の描く要素がブロックだった** —— 拾い上げはブロックを
   **差し出しません**（`switch` の `default`）。だから最後の要素が
   選ばれることがなく、「1 つ先」が一度も出ませんでした。**最後に
   確実に選ばれる線**を置いて、やっと歯が立ちました。

どちらも**細工を入れてみなければ分からなかった**ことです。

**ついでに 1 つ、分からないことが見つかりました。**拾い上げは
`JW_BLOCK` を差し出しません。移植のブロックのコマンドは
**範囲選択**（`o->sel`）から入るので今のところ困りませんが、
**原典で 図形 を 1 回クリックして消せるのかどうかは確かめていません**。
確かめるには原典が要ります。

### 部分円弧の環は、真円の環の部分集合ではありません（2026-09-26、根本原因）

**移植の作りそのものが間違っていました。**移植は部分円弧を、
`src/gen/circle.h` に焼いた**真円の環**から、両端のあいだの一並びを
切り出して描いています。それが正しいのは、**GDI の部分弧の環が
同じ枠の真円の環の部分集合であるとき**だけです。

**そうではありませんでした。**`tools/arcsub.py` が GDI 自身に両方を
聞きます（半径 7・14・19・24・40・61・100 × 8 方向 × 掃引 4 通り、
どれも 2r+1 の枠）:

**224 本のうち 213 本**が、真円の環に無い画素を塗ります。

| 余分 | 半径 | 始点 | 掃引 | 環の大きさ |
|---:|---:|---:|---:|---:|
| 43 | 100 | 4.8224 | 2.6000 | 231 |
| 40 | 100 | 3.2516 | 2.6000 | 231 |
| 31 | 100 | 5.6078 | −1.5708 | 142 |
| 29 | 100 | 4.0370 | −1.5708 | 140 |

**余分な画素は、弧の始点から続く一並び**です（半径 100・始点 4.8224 の
ぶんは +10+99・+16+98・+21+97… と、始点のあたりから順に）。
GDI が環を整数で歩くときの**誤差の初期値が、始点から始めるぶんだけ
違う**、と読めば辻褄が合います。

**向きには依りません。**始点 4.0370 で掃引 +π/2 の弧と、始点 5.6078 で
掃引 −π/2 の弧（同じ弧を逆に辿ったもの）は、まったく同じ画素を出します。
環は **(半径, 両端)** で決まり、辿る向きでは変わりません。

これで説明がつくもの:

* `サンプル` で移植が GDI の画素を取りこぼすのが**弧の途中**だったこと
* 半径も掃引も同じ 2 本（弧 53 と 846）が違う環になること ——
  **始点が違えば環が違う**から
* `Ａマンション平面例` の弧 1656 が半径 1 つぶん外にあること

**これは表にできません。**環が両端に依るので、半径で引く表では持てない。
`tools/gdiarc.c` の注が「だから表に持てない」と書いていたとおりで、
**移植はそれを承知のうえで真円の表を切り出していた**わけです。

**八分円の中には収まりません。**余分な画素がどの八分円に出るかを
数えると、始点の八分円に 52%、次に 26%、その次 15%、さらに次 7% ——
**誤差は八分円の境目を越えて弧の先まで続きます**。GDI は八分円ごとに
歩きを作り直していない、ということです。

**端を八分円の境目に揃えても救われません**（境目に乗せた 224 本のうち
151 本が違う。乗せない 224 本では 213 本）。

**図面が使う半径でも起きます:**

| 半径 | 差の出た弧 | 余分な画素 |
|---:|---|---:|
| 7 | 37 / 64 | 65 |
| **14** | **54 / 64** | **132** |

| **24** | **51 / 64** | **260** |

半径 24 なら 1 本あたり平均 5 画素。`Ａマンション平面例` の 392 画素
（部分円弧は 200 本あまり）と桁が合います。

### 直すには

**表では持てません。**環は (半径, 始点, 終点) で決まるので、半径で引く
表には入りません。**GDI の歩きそのものを書き直すしかありません** ——
始点の画素から、始点から決まる誤差を種にして、整数で環を辿る。

幸い**答え合わせの相手は手元にあります**。`tools/gdiarc.c` がメモリ DC に
描かせて画素を返すので、候補の書き方を何千本もの弧で GDI と突き合わせ
られます（原典も対話デスクトップも要りません）。

### 差の形 —— 流されではなく、1 画素の入れ替え

半径 24・始点 0.11・掃引 π/2 の弧を、真円の環と同じ角度範囲で並べると
**34 画素中ちょうど 4 組の入れ替え**でした:

| 真円の環 | 弧 | |
|---|---|---|
| (23, −3) | (24, −3) | x +1 |
| (20, −12) | (21, −12) | x +1 |
| (18, −16) | (17, −16) | x −1 |
| (8, −22) | (8, −23) | y −1 |

画素の数は同じ（真円の環の四分円ぶんと一致）。**足されるのではなく
置き換わります。**

### 「始点から積んだ誤差」ではありませんでした（否定、2026-09-26）

余分な画素が始点側に偏っていたので、**環が (半径, 始点) だけで決まり、
終点は切り取るだけ**という模型を当てました。そうなら、同じ始点で掃引
だけ変えた 2 本は、**共通の範囲で同じ画素**になるはずです。

`tools/arcsame.py` で測りました（半径 14〜61 × 8 方向 × 3 つのずらし ×
掃引 π/4・π/2・2.6）:

**240 組のうち 48 組しか一致しません。**掃引を伸ばすと、**始点の近くの
画素まで変わります**。

**つまり GDI は弧を全体として組み立てています。**環は **(半径, 始点,
終点)** の 3 つで決まり、歩きを始点から積むだけでは再現できません。
曲線を Bézier に割って描いているなら（割り方が弧の長さで変わるので）
辻褄は合いますが、そこまで合わせるのは別物の作業です。

### GDI の弧は Bézier でした（2026-09-26、内側から確定）

`PolyBezier` で外から当てるのをやめて、**GDI 自身に聞きました**:

```c
BeginPath(dc);
Arc(dc, ...);
EndPath(dc);
GetPath(dc, pts, types, n);
```

返ってきた記録の型は **`6 4 4 4 4 4 4`** —— `PT_MOVETO` のあと
`PT_BEZIERTO` が 6 つ、つまり**三次 Bézier 2 本**です。半径 14・24・61 の
どれでも同じ形でした。

**`GDI` は弧を三次 Bézier に変換しています。**これで、今日の測定が
ひとつ残らず腑に落ちます:

* **環が両端の組で決まる** —— 制御点が掃引全体に依るので当たり前
* **真円の環の部分集合にならない** —— 真円は別の割り方（4 本）
* **半径も掃引も同じでも始点が違えば違う環**

そして決め手:

```
plain Arc 34 pixels, flatten+stroke 34, differ 0
```

**`FlattenPath` して `StrokePath` した画素は、素の `Arc` と 1 画素も
違いません。**`FlattenPath` が返す折れ線は 33 点で、**隣り合う点が必ず
1 画素差**（ほぼ 1 画素刻み）でした。

### 直し方の道筋

1. GDI と同じ**三次 Bézier の制御点**を出す（パスは整数座標なので、
   規則が分かれば一意に決まります）
2. GDI と同じ**平坦化**で折れ線にする
3. 移植の**直線描画に渡す** —— これは既に GDI と画素まで一致しています

**答え合わせは全段で効きます** —— `odd 7` が制御点を、`odd 9` が
平坦化した折れ線を、`odd 8` がその画素を返すので、どの段で食い違ったかが
すぐ分かります。原典も対話デスクトップも要りません。

### 折れ線は粗いものでした（前の節を取り消します、2026-09-27）

**前に「折れ線はほぼ 1 画素に 1 点で、その半分しか弧の画素と一致しない」
「順に結ぶと 2,228 画素になるので並びが崩れている」と書いたのは、
どちらも誤りです。**`tools/gdiarc.c` の外側の条件が `odd == 7 || odd == 8`
のままで **`odd 9` がその枝に入っておらず**、素の `Arc`（しかも 2r の枠）に
落ちて、その**画素**を折れ線として読んでいました。画素は走査順に出るので、
順に結べば長い弦を引くことになります。

**本物の折れ線はこうです**（半径 61・掃引 2.6、140 画素の弧）:

```

```

* 弦の 11.5 度に対する矢は `61(1−cos 5.75°) = 0.31 画素`。GDI の平坦化の

### 平坦化の切り方が決まりました（2026-09-27）

（片 1 は前半だけ深い）。違うのは**止める条件**だけでした。

### 制御点の規則、いま分かっているところ（2026-09-26 深夜）

384 本（半径 7・14・19・24・40・61 × 16 方向 × 掃引 4 通り）を集めて
突き合わせています（`tools/bezfit.py`）。

**分かったこと:**

* **分割は四分円の境目**で。始点が境目にあるときは**退化した Bézier**
  が置かれます
* **半径は `rp` ではなく `rp + 0.5`**。四分円の制御点の歩幅を GDI の
  答えから読むと:

| 半径 | 実測の歩幅 | `k·rp` | **`k·(rp+0.5)`** |
|---:|---:|---:|---:|
| 7 | 4 | 3.87 | **4.14 → 4** |
| 14 | 8 | 7.73 | **8.01 → 8** |
| 19 | 11 | 10.49 ✗ | **10.77 → 11** |
| 24 | 14 | 13.25 ✗ | **13.53 → 14** |
| 40 | 22 | 22.09 | **22.37 → 22** |
| 61 | 34 | 33.69 | **33.96 → 34** |

  `k = 4/3 tan(θ/4)` は標準のまま。**半径だけが違っていました。**

**まだ合っていないこと:**

* 退化した片が**先頭に来るか末尾に来るか**。始点が境目ちょうどの 2 例で
  割れます —— 半径 61・始点 270 度は先頭、半径 24・始点 0 度は末尾
* 半径 24・掃引 1.57（90 度より僅かに手前）で、GDI は**四分円まるごとの
  制御点**を使い、余りを退化した片にします。**丸めた終点が 90 度の点と
  同じ**になるからだと読めます

**次の見立て:** GDI は**先に両端を整数に丸め**、その丸めた点のあいだを
四分円で割って、各片の Bézier を**丸めた端点から**組んでいる。
それなら上の 2 つとも説明がつきます。

### 制御点の形（`odd 7` で集めたもの）

きれいな四分円（半径 24、上 → 左）:

```
MOVETO (0,-24)
BEZIER (-13,-24) (-24,-13) (-24,0)
```

標準の円弧 Bézier（`k = 4/3 tan(θ/4)`、四分円なら 0.5523）で
`k·R = 0.5523 × 24 = 13.25` —— **13 に丸めたもの**です。

**四分円ごとに 1 本**で、余りは**退化した Bézier**として出ます。
半径 14 の 90 度の弧は

```
MOVETO (14,0)
BEZIER (14,-8) (8,-14) (0,-14)
BEZIER (0,-14) (0,-14) (0,-14)      ← 退化
```

始点が四分円の境目でないときは、前にも退化したものが付きます
（`q3` は 3 本で、先頭と末尾が退化）。

**枠の中心と半径がやっと腑に落ちました。**`Arc` の矩形は右下が排他なので、
`(cx-rp, cy-rp, cx+rp+1, cy+rp+1)` が覆う画素は `cx-rp` から `cx+rp` ——
**中心は `cx` ちょうど、半径は `rp` ちょうど**です。今日「環の画素が
半径 14.5 に乗っていない」と悩んでいたのは、これを取り違えていたため
でした。

**まだ合っていないのは始点の置き方**です。与えた点を通る光線と円の交点を
丸めるだけでは、いくつかの例（`r14` は `(14,0)`、`r7` は `(7,-1)`）が
揃いません。ここは数を集めて詰めます。

### （旧）Bézier 説 —— 外から当てた版

「両端の組で決まる」という性質は、歩きを積む模型では出せませんが、
**曲線を Bézier に割る**なら自然に出ます（制御点が掃引全体に依るので、
遠い端を動かすと始点近くの形まで変わる）。

`tools/gdiarc.c` に `odd 6` を足して、**同じ弧を `PolyBezier` で**
描かせ、`Arc` と画素を比べました（`tools/arcbez.py`、360 本）。

* **短い掃引（π/4）なら差は 1〜3 画素**（弧そのものが 9〜28 画素）
* 長い掃引（2.6）では大きく外れる

**確かめきれない理由が 2 つあります:**

1. `PolyBezier` は制御点が **`POINT`（整数）** です。こちらで丸めた
   ぶんの誤差が入ります。GDI が内部で弧を Bézier に直すなら、
   そこは固定小数のままのはずで、同じ土俵に乗せられません
2. 長い掃引の割り方（どこで区切るか）が GDI と同じとは限りません

**近さは示唆的ですが、証拠にはなりません。**この道で詰めるには
`PolyBezier` ではなく、GDI の内部と同じ精度で Bézier を渡せる口が要ります。

### 枠は 2r か 2r+1 しかありません —— 原を読み直しました（2026-09-26）

### `+0x44` のビット 0x10 は描画を変えません（2026-09-26、後で言い方を直しました）

### 円弧の端は「角」ではなく「画素」で決まります（974 → 973）

原典は GDI に角度を渡しません。**端の画素**を渡します——

    (int)(rp * cos a) 右へ、 -(int)(rp * sin a) 下へ

**切り捨て**です。GDI はその画素を通る半直線で環を切るので、半径 24 の
円の 30 度の端は、本当は `atan2(12, 20)` = **30.96 度**の端です。移植は
`a` をそのまま使っていました。`ray_angle()` を入れて、始点も終点も
**丸めたあとの向き**で探すようにしました。15 枚の合計は **974 → 973**
（`Ａマンション平面例` −2、`サンプル` +1）—— ほとんど動きませんが、
原典がやっていることではあります。残差の半分以上が円弧の端の 3 画素内
だという勘定のほうは、**端の選び方では説明がつかない**と分かりました。

**残りはほとんど円弧です。**残差 974 のうち **752 画素**が、その図面の
どれかの円弧の環の上（±1.5 画素）に乗っています。中心を 50 画素ずらした
対照ではそれぞれ 142・0・10 なので、まぐれではありません。

| | 円弧の環の上 | 残差 | 円弧の数 |
|---|---:|---:|---:|
| Ａマンション平面例 | 397 | 412 | 215 |
| 日影図 | 214 | 275 | 6（どれも点線） |
| サンプル | 75 | 102 | 64 |
| 天空率表 | 61 | 98 | 35 |

**そのうち半分以上は「端」です。**`Ａマンション平面例` の 412 のうち
**221**、`サンプル` の 102 のうち **66** が、弧の端（半径ベクトルの先）
から 3 画素以内にあります。1 本あたり 1〜2 画素、つまり**始点と終点の
画素の選び方**がまだ原典と違う、ということだと思います。

**潰した筋:**

* **GDI の `Arc` と `Ellipse` は同じ環を描きません**（半径 24 で 12 画素
  違う）。原典が呼ぶのは `Arc`、移植の表は `Ellipse` から採ったものです。
  ——**が、これは原因ではありませんでした。**同梱の図面で、2 つが食い違う
  画素のうち弧の振り角に入るものを数えると、`Ａマンション平面例` で
  原典 7 対 6、移植 6 対 5（`サンプル` は 0 対 0）。どちらの環かでは
  説明が付きません。
* **端の選び方を「振り角に入る画素すべて」に変えても**、GDI の `Arc` との
  食い違いは 3,134 → 3,080 画素（半径 5〜40 × 5 つの始角 × 4 つの振り角、
  720 本）にしかなりません。
* **半径ベクトルの丸め**（原典は `(int)(rp*cos a)` と切り捨て）に合わせても
  ほとんど動きません（3,138 / 3,084）。始角・振り角を**切り捨てた
  半径ベクトルの角**に置き換えても同じ（半端な角を混ぜると
  5,571 → 5,519）。
* **実線の弧も折れ線で描く**（`doc+0x1730` の閾値がとても小さい、という
  読み）**ではありません。**全部の弧を折れ線に回すと 15 枚の合計が

  `日影図` だけは 275 → 262 とわずかに良くなるので、点線の弧の
  刻み方にはまだ何かあるのかもしれません。
* **線の切り取りを止める**のも違います —— 974 → **9,578**。移植の
  切り取りはおおむね正しい、ということです。ただし原典は**矩形を 2 つ**

## ペンの太さ（入っています）

**図面はペンごとに太さを持っていて、原典は画面でもそれを使います。**
既定の表は `pen 6 = 2`・`pen 7 = 3`・`pen 8 = 5` で、`Test3.jww` の青い
破線の枠（線色 6・線種 2）は原典では **559 行と 560 行の 2 行**、
**427 列と 428 列の 2 列**に出ます。移植の `pen_wide()` は常に 1 を返して
いたので、そこだけで **533 画素**ずれていました。`Test3` は
**825 → 294 画素**、15 枚の合計は **4,976 → 4,445**。

太さの出どころは `FUN_004db560` です。

```c
if (*(int *)(in_ECX + 0x2c58) == 0)  CreatePen(PS_SOLID, width, colour);
else  ExtCreatePen(style | PS_GEOMETRIC | PS_JOIN_BEVEL, width, &brush, 0, 0);
```

**太い線は正方形の判子を線に沿って押したものではありません。**GDI は端を
丸め、しかも偶数の太さでは左右対称ですらありません。`tools/gdiwide.c` が
GDI に直接聞いて `decomp/res/widepen.txt` に書き出し、`tools/mkwide.py` が
`src/gen/wide.h` にします。表は**線を横切る向きのずれ `d` ごとに、線に
沿った開始と終了のずれ**です（`d` は `-(w/2)` から `(w-1)/2`）:

* **太さ 1** は `{0, -1}` —— `LineTo` は最後の点を描きません。同じ表で
  まかなえるので、細い線も太い線も 1 つのループで済みます。
* **偶数の太さ**は余分の画素が**水平線なら上・垂直線なら左**に出ます。
* **水平線のいちばん外側の行は 1 画素遅れて始まります**（`{+1, 0}`）。
  移植が最初これを落として、原典が 2 画素の破片を並べるところに 3 画素を
  並べ、152 画素余計に塗っていました。
* **太さ 3 以上は端が丸い**ので、線の両端に少しはみ出します
  （太さ 5 なら中の 3 行が ±2、外の 2 行が ±1）。

移植側は `stroke()` が**ずれごとに 1 本ずつ**走らせます
（`stroke_at()`）。破線は 1 つの run が 1 本の `LineTo` なので、run ごとに
端の丸めが付きます —— そこが表と合っていないと、破線の数だけ誤差が出ます。
画素単位で歩く経路（点線・楕円の弦）には run がないので `wide_dot()` が
真ん中の形だけを押します。

残りは**線が交わる角の 6 画素**だけです（GDI の継ぎ目の規則）。
